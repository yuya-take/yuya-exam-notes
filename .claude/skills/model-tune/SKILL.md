# /model-tune

引数: `$ARGUMENTS`

スキルの文面は、書いた時点のモデルの癖に合わせて調整してある。モデルが変わると、前のモデル向けの対策が逆効果になることがある。例えば次のようなもの。
- 強調表現が、過剰な反応を招く
- 「重要なものだけ報告」という絞り込みが、見落としを増やす
- 「先に計画せよ」という指示が、計画のしすぎを招く

このスキルは、そうした箇所を公式の一次情報を根拠に見つけて直す。

根拠にするのは、このスキルの実行中に取得した公式ドキュメントに書かれていることだけ。モデルや Claude Code の仕様は学習データより新しいことが多いので、記憶にある仕様は使わない。

## 1. 前回からの差分を把握する

`${CLAUDE_SKILL_DIR}/history.md` を読み、前回の対象モデル、Claude Code のバージョン、反映した変更を確認する。

対象モデルは、引数で指定があればそれにする。無ければ、公式のモデル一覧で最新の Opus にする。前回と同じモデルなら、Claude Code 側の仕様変更だけを点検する。

## 2. 公式情報を集める

モデル側と Claude Code 側は別々に調べられるので、それぞれ1つずつサブエージェントに調べさせ、並列で進めてよい。調査の記録は持ち込まず、要点だけを受け取る。

**モデル側（対象モデルの特性）**
- `claude-api` スキルを読み込み、同梱の `shared/model-migration.md` から対象モデルの節（Behavioral shifts と Migration Checklist）を読む。`shared/prompt-audit.md` は全文を読む。`prompt-audit.md` は、古いモデル向けの書き方を見つけるための判定基準で、ステップ 3 の点検の基準になる
- https://platform.claude.com/llms.txt からページ一覧をたどり、対象モデルの次のページを読む
  - 「What's new」
  - 「Prompting Claude <モデル名>」
  - 移行ガイド
  - effort のページ

**Claude Code 側（スキルの書式と設定）**
- https://code.claude.com/docs/llms.txt からページ一覧をたどり、次のページを読む
  - skills（frontmatter と、`$ARGUMENTS` などの文字列置換）
  - sub-agents
  - model-config（effort の既定値）
  - settings reference と permissions
  - 組み込みコマンドの一覧
- クラウドのセッション（`mcp__claude-code-remote__*` のツール）のドキュメント。`/orchestrate` が使うツール名と引数がまだ有効かを確かめる
- claude-code-guide エージェントに聞いてもよい。ただし、回答に出てきた設定キーや値の型は、ドキュメント本文で確かめてから使う

集めた内容を、次の観点で「モデルプロファイル」として短くまとめる。
- **effort と思考:** effort の既定値と、推奨される使い分け。思考の扱い
- **前のモデルからの挙動の変化:** 応答の長さ、サブエージェントの使い方、自分の作業の検証、タスクの範囲の広げ方、指示への従い方、報告の絞り方
- **公式が削除・書き換えを勧めている指示のパターン**
- **Claude Code の変更:** 追加・廃止・変更された frontmatter のフィールド、設定キー、permission の書式、組み込みコマンド

## 3. 点検する

**対象:**
- `.claude/skills/*/SKILL.md` と、スキルに同梱しているファイル（`exam-add/template.md` など）
- `CLAUDE.md`
- `.claude/agents/*.md`（frontmatter の `tools`・`model` などが今の仕様で有効か、指示が今のモデルに合っているか）
- `.claude/settings.json`（フックの書式を含む）
- `.claude/hooks/`・`.claude/scripts/`・`.github/workflows/`（フックの入出力の仕様が変わっていないか）
- `README.md` のスキル一覧

**基準:** `prompt-audit.md` のパターン（圧力表現、API の機能で置き換わった足場、手順の過剰指定、旧モデル向けの名残、設定ファイルの陳腐化）と、ステップ 2 のモデルプロファイル。

このリポジトリでずれやすい点は、毎回確認する。
- **`/orchestrate`:**
  - 作業セッションへの指示が、範囲を広げすぎない書き方になっているか
  - 作業セッションへの指示が、逆に細かすぎないか
  - 検証の工程（範囲・形・事実の確認）の分担が、モデルの推奨と合っているか
  - 使っているツール名と引数が、今も有効か
- **`/study`:** ノートの構成や「未確認と書く」指示が、モデルの癖に対して過不足ないか
- **`/quiz`:** 問題作成の指示が、今のモデルで良い問題を生むか。正解の位置の偏りや、明らかに誤りの選択肢を防げているか
- **frontmatter:** `disable-model-invocation`、`argument-hint` などが、今の仕様で有効か
- **スキル名:** 組み込みコマンドと衝突していないか

次のものは残す。
- このリポジトリ固有の文脈（ディレクトリ構成、チェックリストの書き方）
- 共有ファイルを作業セッションに触らせないなどの、衝突を防ぐ規則
- 理由の付いた禁止事項（本番の問題を再現しない、など）

**Claude 関連の資格がある場合:** モデルや Claude Code の変更は、試験範囲やノートの内容にも関わる（例: `ccaf`）。点検の対象はスキルだが、内容が古くなったと思われるノートがあれば一覧にして、報告で `/exam-update` を勧める。

## 4. 報告して承認を得る

指摘ごとに、次の5つを示す。
- 場所（`file:line`）
- 該当箇所の引用
- 根拠（公式ページの URL か、同梱リファレンスの節）
- 重要度（高 / 中 / 低）
- 修正案

根拠を示せないものは「要確認」として別にまとめ、修正案には含めない。指摘が無ければ、そう報告して、ステップ 6 の記録だけを行う。

修正は、`AskUserQuestion` で承認を得てから行う。指摘が多いときは、重要度ごとにまとめて聞く。

## 5. 修正して確かめる

承認された範囲を修正し、次を確かめる。
- `.claude/settings.json` が JSON として読めること（`python3 -m json.tool`）
- 各 `SKILL.md` の frontmatter が YAML として読め、`name` がディレクトリ名と一致すること
- スキルを削除・改名した場合は、次の場所に参照が残っていないことを grep で確かめる
  - `README.md`
  - `CLAUDE.md`
  - ほかのスキル
- 読むだけのスキル（`/progress`）を一度実行し、エラーなく集計できること

## 6. 記録してコミットする

`${CLAUDE_SKILL_DIR}/history.md` の先頭に、今回の記録を追加する。
- 日付と対象モデル
- Claude Code のバージョン（`claude --version`。取れなければ「不明」）
- 参照した主な公式ページ
- モデルプロファイルの要点
- 反映した変更の要約（変更が無ければ「変更なし」）

`chore: <対象モデル>に合わせてスキルを調整` でコミットする。PR は、ユーザーに頼まれたときだけ作る。
