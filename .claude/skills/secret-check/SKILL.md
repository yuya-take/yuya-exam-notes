# Secret Check

変更に機微情報が含まれていないかを、2段階で調べる。

- **段階1 機械的な検出:** パターンで拾えるもの。PreToolUse フックとしても、`git commit` と `git push` のたびに自動で動いている
- **段階2 文脈での判断:** パターンでは拾えないもの。このスキルが受け持つ

見つかったものの値そのものは、チャットにも、コミットメッセージにも、PR にも書かない。種類と場所だけを示す。

## 段階1: 機械的な検出

```bash
python3 .claude/hooks/secret_scan.py $ARGUMENTS
```

引数が無いときは、HEAD からの全変更（ステージ済み・未ステージ・未追跡）を調べる。検出するものは次のとおり。
- API キー・トークン・秘密鍵・パスワードの代入
- メールアドレス・電話番号
- 受験者 ID・認定番号・バウチャーコード
- `.env`・鍵・認証情報のファイル
- スコアレポートや認定証の画像・PDF

## 段階2: 文脈での判断

`secret-reviewer` エージェントに、段階1と同じ範囲（`--range` の値、`--staged`、または「HEAD からの全変更」）を伝えて判断させる。自分で書いた変更を自分で見ると見落としやすいので、別のエージェントに任せる。エージェントが使えないときは、同じ観点で自分で差分を読む。

観点は次のとおり（`secret-reviewer` にも同じものが書いてある）。

| 観点 | 例 |
|---|---|
| 個人を特定できる情報 | 本名、住所、勤務先、顔写真、受験会場と日時の組み合わせ |
| 試験の守秘義務 | 本番で見た問題・選択肢の再現、「本番でこれが出た」という記述。多くの資格は受験時に守秘義務に同意しているため、ノートにも練習問題にも書かない |
| 本人の結果の詳細 | スコアレポートの数値や、ドメインごとの得点の書き写し。残したいときは、ユーザーに確かめてから「合格」「不合格」程度にとどめる |
| 社内・非公開の情報 | 勤務先の内部情報、非公開の URL・ホスト名、有料教材の本文の転載 |
| 認証情報の断片 | パターンに合わない形のトークン、接続文字列、署名付き URL |

## 見つかったとき

1. 種類と場所（`file:line`）を一覧にする。値は書かない
2. 直し方を決める
   - **キーやトークン:** 消すか、`<YOUR_API_KEY>` のようなプレースホルダに置き換える
   - **個人情報:** 消すか、一般化する（「都内の会場」など）
   - **本番問題の再現:** その部分を消す。学んだ論点だけを、公式ドキュメントに基づく一般的な書き方で残す
   - **誤検知:** `.claude/secret-allowlist` に、除外の正規表現を1行足す。足した理由を、同じファイルにコメント（`#`）で書く
3. まだコミットしていなければ、直してから進める
4. **既にコミット済み（push 前）のとき:** 直したうえで、どう履歴から消すか（そのコミットを直す、など）をユーザーに確かめる。履歴の書き換えは、確認なしにしない
5. **既に push 済みのとき:** 消しても履歴とキャッシュに残る。キーやトークンなら、すぐに失効・再発行するようユーザーに伝える。これを最優先にする

## 結果の伝え方

呼び出し元（`/pr` や、コミットの前の確認）には、次のどちらかを返す。
- **問題なし:** 段階1と段階2で、何を調べたか
- **要対応:** 種類と場所の一覧と、直し方

要対応のまま、コミット・push・PR 作成に進まない。
