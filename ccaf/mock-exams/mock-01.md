## シナリオ1: カスタマーサポートのエージェント

家具の通販会社「キノハ家具」は、Claude Agent SDK でカスタマーサポートのエージェントを作っている。エージェントは自社の MCP サーバーのツール（`lookup_member`、`get_order`、`issue_refund`、`change_delivery`、`open_handoff_ticket` など）で会員・注文・配送のシステムを操作する。返品・配送の変更・請求の食い違いなど、曖昧さの大きい問い合わせを扱い、1回の対応で解決する割合を上げつつ、人の担当者に回すべきものは回すことを目指している。

**問1** キノハ家具では、本番前の検証のために Messages API で自前のエージェントループも書いている。長い返品の相談で、応答の `stop_reason` が `max_tokens` になり、最後の `tool_use` ブロック（`issue_refund` の呼び出し）が途中で切れていた。今のループは、`stop_reason` が `tool_use` 以外なら最終回答として顧客に返している。最も適切な直し方はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="B" data-domain="1" markdown>

- A. 切れた `tool_use` の入力のうち読める部分だけで `issue_refund` を実行し、ループを続ける
- B. `max_tokens` を完了と扱わず、上限を上げて同じリクエストを送り直すよう分岐を足す
- C. システムプロンプトに「応答は短くまとめ、上限に達しないこと」と書き足して様子を見る
- D. `max_tokens` のときは、それまでのテキストに「以上です」と足して顧客に返す

</div>

??? success "答えと解説"
    **正解: B。** `max_tokens` は「出力が上限で切れた」ことを示し、完了ではない。途中で切れた `tool_use` は、上限を上げて送り直す。

    - A: 切れた入力は不完全なので、そのまま返金を実行すると誤った処理になりうる
    - C: 指示で長さを抑えても、上限で切れる応答への対処（分岐）が無いままになる
    - D: 途中で切れた応答を完了として扱う点が変わらない

    根拠: [エージェントループと stop_reason による制御](../notes/01-agentic-architecture/agentic-loop-stop-reason.md)

**問2** 返品では、預かった荷物が倉庫に届いたことを `get_order` で確かめるまで返金しない決まりがある。そこで PreToolUse フックで前提ゲートを作り、`get_order` で到着済みと確認した注文 ID を記録して、`issue_refund` の注文 ID がその記録に無ければ止めている。ところが、記録はプロセス全体で1つの集合として持っており、同時に動くほかの顧客との会話で確認された注文 ID でも通ってしまう事例が見つかった。最も適切な直し方はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="A" data-domain="1" markdown>

- A. 確認済みの記録をフックの入力の `session_id` ごとに持ち、その会話の確認だけで判定する
- B. 確認済みの集合を1時間ごとに空にし、古い確認では返金が通らないようにする
- C. ゲートをやめ、システムプロンプトに「その会話で確認した注文だけを返金すること」と書く
- D. 集合に入れる前に `get_order` をもう一度呼び、到着を二重に確かめてから記録する

</div>

??? success "答えと解説"
    **正解: A。** ゲートは「確認済みの値を記録し、後続の呼び出しの値と照合する」もの。記録は会話ごとに持つ必要がある。フックの入力には `session_id` があるので、セッションごとに確認済みの状態を持てる。

    - B: 1時間以内なら、ほかの会話の確認で通る問題が残る
    - C: お金に関わる順序を、確率的にしか守られないプロンプトに戻すことになる
    - D: 確認を二重にしても、別の会話の記録で通る問題は変わらない

    根拠: [ワークフローの順序をプログラムで強制する](../notes/01-agentic-architecture/programmatic-workflow-enforcement.md)

- B. `allowedTools` に `mcp__kinoha__*` を足し、MCP のツールを自動で許可する
- C. `.mcp.json` のサーバー名を変え、組み込みのツールとの名前の衝突を避ける

??? success "答えと解説"
    **正解: A。** Agent SDK では、MCP サーバーは `mcpServers` オプションでコードから渡すか、`settingSources` に `"project"` を含めて `.mcp.json` を読ませる。読み込み元を user だけに絞ると、`.mcp.json` は読まれない。

    - B: `allowedTools` は許可の設定で、サーバーを読み込む設定ではない
    - C: 名前は `mcp__<サーバー名>__<ツール名>` の形で、組み込みのツールと衝突していない
    - D: サーバーにつながっていないので、ツールそのものが存在しない

    根拠: [Claude Code と Agent SDK への MCP サーバーの組み込み](../notes/02-tool-design-mcp/mcp-server-integration.md)

**問4** 顧客が「山田です。先月買ったソファの件で」と書いてきた。エージェントが氏名で `lookup_member` を呼ぶと、「山田」姓の会員が3人返った。3人とも先月ソファを買っている。次の一手として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="C" data-domain="5" markdown>

- A. 3人のうち、注文日がいちばん新しい会員を本人とみなして手続きを進める
- B. 本人を特定できないので、`open_handoff_ticket` で人の担当者に引き継ぐ
- C. 注文番号や登録のメールアドレスなど、本人を1人に絞れる情報を顧客に尋ねる

??? success "答えと解説"
    **正解: C。** ツールが複数の候補を返したら、経験則で選ばずに、追加の識別子を尋ねて1人に絞る。

    - A: 「いちばん新しい注文」のような経験則で選ぶと、別人の注文を操作するおそれがある
    - B: 識別子を1つ尋ねれば解決できる。人に回す基準（人を求められた、方針の空白、前進できない）に当たらない
    - D: ほかの会員の注文の内容を見せることになり、個人情報の扱いとして不適切

    根拠: [エスカレーションの基準と、曖昧な依頼の確かめ方](../notes/05-context-reliability/escalation-ambiguity.md)

<div class="quiz" data-answer="C" data-domain="1" markdown>

- A. システムプロンプトに「止められたら、同じ呼び出しを繰り返さないこと」と書く
- B. deny をやめ、`updatedInput` で配送日を元の日付に書き換えてから通す
- C. 説明を `permissionDecisionReason` に移し、次に呼ぶツールを伝える

    - B: 呼び出しは「成功」扱いになり、モデルは配送日を変えられたと誤解する。顧客の依頼も宙に浮く
    - D: 説明文の指示は確率的にしか守られない。「必ず」の規則はフックで止める

- A. このリクエストだけ `tool_choice` を `{"type": "none"}` にし、ツールを呼ばせない

    - B: ツールの一覧を変えると、ツール定義のキャッシュを作り直すことになる
    - C: `any` はどれかのツールを必ず呼ばせる設定で、目的と逆になる
    - D: プロンプトでの指示は確率的にしか守られない

**問7** 1回の対応で複数の件を扱うため、件ごとの注文番号・金額・状態を「事実のブロック」にし、要約された会話の外で毎回のプロンプトに入れている。ブロックは対応の最初に、`get_order` の結果から作る。ある対応で、顧客が途中でテーブルの返品を取り下げたのに、後半でエージェントが取り下げ前の返金額を案内した。最も適切な直し方はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="B" data-domain="5" markdown>

- A. 状態が変わるたびに、新しい事実のブロックを古いブロックの後ろに書き足していく
- B. 件の状態が変わったら、事実のブロックの該当する件をその都度書き換える
- C. 事実のブロックをやめ、件ごとの状態は会話の要約の中で管理させる

??? success "答えと解説"
    **正解: B。** 事実のブロックは、正確さが要る事実（金額・注文番号・状態）を要約の外で保つためのもの。状態が変わったら、ブロックの中身も書き換えて最新に保つ。

    - A: 古い状態と新しい状態が両方残り、どちらが今の状態かを取り違える
    - C: 正確さが要る事実を要約に任せると、要約を重ねるうちにぼやける
    - D: 間違いの元は事実のブロックの古い状態で、要約ではない

    根拠: [長い対話で重要な事実を保つ](../notes/05-context-reliability/preserving-key-facts.md)

**問8** 「配送日の変更は、今日から30日より先の日付にはできない」という規則を守らせるため、フックで `change_delivery` の日付を確かめている。しかし、(1) 規則に反する変更が配送システムに登録されてしまうことがある、(2) 会員の照会など、関係のないツールを呼ぶたびにも確認が走り、応答が遅い、という2つの問題が出た。フックは PostToolUse に、matcher を付けずに登録してある。直し方として適切なものはどれか。（2つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="B,E" data-domain="1" markdown>

- A. PostToolUse のまま、規則に反する結果を見つけたら `systemMessage` で顧客に知らせる
- B. 確認を PreToolUse に移し、規則に反する呼び出しを実行前に deny で止める
- C. フックをやめ、システムプロンプトに30日の規則を太字で書いて守らせる
- D. 関係のないツールでも確認が走るのは安全側なので、そのまま全ツールに残す
- E. matcher で `change_delivery` を指定し、そのツールの呼び出しのときだけ動かす

</div>

??? success "答えと解説"

    - A: PostToolUse は実行の後に動くので、登録はもう済んでいる。知らせても止めたことにならない
    - C: 「必ず」守らせる規則をプロンプトだけに任せると、確率的にしか守られない
    - D: matcher なしの登録は全ツールで動く。安全には何も足さず、遅さだけが残る

    根拠: [Agent SDK のフックによるツール呼び出しの遮断とデータの正規化](../notes/01-agentic-architecture/sdk-hooks-interception.md)

**問9** Messages API で書いた検証用のループで、最初のリクエストを `{"type": "tool", "name": "classify_inquiry"}` にして問い合わせの種類を必ず判定させている。判定の精度を上げようと、同じリクエストで手動の拡張思考（`thinking: {"type": "enabled", ...}`）も有効にしたところ、リクエストがエラーで拒否された。判定を必ず最初に通すことが最優先で、考えさせることは必須ではない。最も適切な対応はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="C" data-domain="2" markdown>

- A. 拡張思考は有効のまま、`tool_choice` を `any` に変えて送り直す
- B. 拡張思考の思考の予算を小さくして、`tool` での強制と一緒に送り直す
- C. 拡張思考を外し、最初のリクエストの `tool` での強制はそのまま残す
- D. 強制をやめて `auto` に戻し、判定するかどうかも拡張思考に任せる

</div>

??? success "答えと解説"
    **正解: C。** 手動の拡張思考は、`any` / `tool` による強制と併用できない。判定を必ず通すことが最優先なら、思考を外して強制を残す（考えさせたいときは、`auto` のままプロンプトでツールを指示する方法になるが、呼ぶ保証は無くなる）。

    - A: `any` も強制の一種なので、手動の拡張思考とは併用できない
    - B: 予算の大小の問題ではない。強制と手動の拡張思考の組み合わせそのものが拒否される
    - D: `auto` では判定のツールを呼ぶ保証が無く、最優先の要件を満たせない

    補足: 試験ガイドの書き方（`any` / `tool` で強制する）で答えを決めた。現行ドキュメントでは、新しい一部のモデルは `any` / `tool` 自体を受け付けず、`auto` と strict tool use などを使うよう案内している。

    根拠: [tool_choice の設定（auto / any / 特定ツールの強制）](../notes/02-tool-design-mcp/tool-choice.md)

**問10** 顧客から、4点セットで買ったダイニング家具のうちチェア1脚だけを返品したい、セット割引とクーポンを使っている、という相談が来た。返品の方針は、セットの一部返品と、そのときの割引の再計算の方法を定めている。計算は込み入っているが、必要なツールはそろっている。エージェントの対応として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="C" data-domain="5" markdown>

- A. 計算が込み入っていて誤りやすいので、`open_handoff_ticket` で人の担当者に回す
- B. 方針から外れるおそれがあるので、返品の可否は答えずに後日の連絡を約束する
- C. 方針に沿って割引を再計算し、返金額を示して、エージェント自身で手続きを進める
- D. 割引が2種類以上重なる返品は、計算の誤りを避けるため一律に人の担当者に回す

</div>

??? success "答えと解説"
    **正解: C。** 込み入っていても方針の範囲内なら、エージェントが自分で解決する。人に回す基準は「人を求められた」「方針の例外・空白」「意味のある前進ができない」で、「複雑そう」だけでは回さない。

    - A: 複雑さは人に回す基準ではない。1回の対応で解決できる案件を手放すことになる
    - B: 方針は一部返品を定めているので、方針から外れるおそれは無い。先送りは解決を遅らせるだけ
    - D: 「割引が重なる」は複雑さの目印にすぎず、方針の空白ではない。基準でないもので一律に回すと、解決できる案件を手放す

    根拠: [エスカレーションの基準と、曖昧な依頼の確かめ方](../notes/05-context-reliability/escalation-ambiguity.md)

**問11** 請求の食い違いをエージェントでは解決できず、人の担当者に引き継ぐことにした。担当者のチケットのシステムでは、エージェントと顧客の会話は見られない。エージェントが作ったチケットの下書きは次のとおり。`{"member_id": "M-20931", "order_id": "K-77812", "amount_diff": 4800, "cause": "クーポンの二重適用"}`。この下書きに足すべきものとして最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="D" data-domain="1" markdown>

- A. チケットの件名として、「請求の件」のように短くまとめた見出し
- B. 調査で呼んだツールの入力と出力を、呼んだ順にすべて並べた記録の全文
- C. 顧客の苛立ちの強さを数値にしたスコアと、その根拠になった発言の引用

</div>

    - A: 件名を整えても、受け手が何をすべきかは分からないまま
    - B: 記録の量が多く、要点が埋もれる。読み解く手間を受け手に回している

## シナリオ5: Claude Code を CI/CD に組み込む

物流向けの SaaS を作る「ツミキ物流システム」は、CI のパイプラインに Claude Code を組み込んでいる。PR ごとに自動でコードをレビューしてインラインコメントを付け、足りないテストを提案し、夜間にはリポジトリ全体の点検も回す。リポジトリは複数のサービスとパッケージを含むモノレポで、開発者も手元で Claude Code を使っている。指摘は開発者がすぐ動ける具体的なものにし、誤検知を減らすことが目標である。

**問31** レビューのジョブは `claude -p` に `--output-format json` と `--json-schema` を付けて実行し、後段のスクリプトが `structured_output.findings` を読んでインラインコメントを投稿している。ところが、ジョブが成功で終わったのに、コメントが1件も投稿されていない PR が時々ある。調べると、その実行では Claude が依頼の一部を断っており、出力に `structured_output` が無かった。後段のスクリプトの直し方として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="A" data-domain="3" markdown>

- A. `structured_output` の有無を確かめ、無ければジョブを失敗として扱い、出力を残す
- B. スキーマの欄をすべて任意にして、`structured_output` が毎回必ず作られるようにする
- C. コメントが0件のジョブは、`structured_output` が出るまで同じコマンドを実行し直す
- D. `structured_output` が無いときは、`result` の文章をそのまま PR のコメントとして投稿する

</div>

??? success "答えと解説"
    **正解: A。** `--json-schema` を付けても、Claude が依頼を断ったときなどは `structured_output` が無いことがある。使う前に有無を確かめ、無ければ失敗させて原因を追えるようにする。

    - B: 断ったときに `structured_output` が無い、という事情は欄を任意にしても変わらない
    - C: 断った理由を確かめないまま繰り返すことになり、コストだけが増える。指摘が本当に無い PR でもコメントは0件になるので、0件だけでは失敗と見分けられない
    - D: 形の決まっていない文章が、インラインコメントの形を前提にした投稿の処理に流れ込む

    根拠: [CI での Claude Code の非対話実行と構造化出力](../notes/03-claude-code/ci-non-interactive.md)

    **正解: C。** インタビューの結果は SPEC.md のような文書にまとめ、新しいセッションでそれを元に実装する。実装は、論点が整理された文書と、まだ使われていないコンテキストから始められる。

    - A: インタビューのやりとりでコンテキストが埋まったまま実装に入ることになる
    - B: CLAUDE.md は毎回読まれる。この機能を作るときだけ要る仕様を置く場所ではない
    - D: 洗い出した論点を活かさず、手戻りを後ろに回すだけになる

    根拠: [Claude Code での反復的な改善](../notes/03-claude-code/iterative-refinement.md)、[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)

**問59** 抽出全体の正答率が 96% に達したので、人のレビューを減らし、確信度の高い抽出は人を通さずに登録したいという声が出ている。扱う文書の9割は請求書で、賃貸借契約書と修繕の見積書は合わせて1割ほどである。自動で通す範囲を広げる前に行うこととして、適切なものはどれか。（2つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="A,D" data-domain="5" markdown>

- A. 文書の種類ごと・フィールドごとに正答率を出し、どの層でも基準を満たすかを確かめる
- B. 全体の正答率が 96% あるので、それを根拠に全種類の文書を自動で通す
- C. モデルが出す確信度を、検証用のデータで較正せずに、そのまましきい値として使う
- D. 自動で通すものからも、層別に無作為に抜き取り、誤り率を測り続ける仕組みを作る
- E. 確信度の高い抽出は誤りが無いとみなし、抜き取りの対象から外す

</div>

??? success "答えと解説"
    **正解: A と D。** 全体の正答率は件数の多い請求書に引っ張られ、件数の少ない種類やフィールドの弱さが埋もれる。層ごとに確かめ、自動で通すものも層別に抜き取り続ける。

    - B: 1割の文書の正答率が低くても、全体の数字には表れにくい
    - C: 確信度は、検証用のデータで較正してからしきい値に使う
    - E: 確信度の高いものを見ないと、誤り率の変化や新しい誤りの型に気づけない

    根拠: [人によるレビューの流れと確信度の較正](../notes/05-context-reliability/human-review-confidence-calibration.md)

**問60** 開発者が Claude Code で、どのフィールドの検証がパイプラインのどこで行われているかを、2時間かけて調べてきた。探索の出力でコンテキストがほぼいっぱいになったが、これまでに分かった「各フィールドの検証の場所」はこのあとの改修で使う。次の一手として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="B" data-domain="5" markdown>

- A. `/clear` で会話を空にし、続きの調査を最初から改めてやり直させる
- B. `/compact` に「各フィールドの検証の場所」を焦点として指定して詰める
- C. 何もせずに調査を続け、コンテキストの扱いは自動の圧縮にすべて任せる
- D. 新しいセッションを開き、前の調査のことは特に伝えずに続きを頼む

</div>

??? success "答えと解説"
    **正解: B。** 探索の出力で文脈が満杯なら、`/compact <焦点>` で今後も使う論点を指定して詰める。重要な発見は、ファイル（スクラッチパッド）に書き出しておくとさらに安全。

    - A: `/clear` は別の作業に移るためのもの。2時間分の発見を捨てることになる
    - C: このセッションでは何を残すかを指示していないので、自動の圧縮でどの発見が残るかが分からない
    - D: 前の発見が引き継がれず、同じ探索をやり直すことになる

    根拠: [大きなコードベースの探索でのコンテキスト管理](../notes/05-context-reliability/large-codebase-context.md)
