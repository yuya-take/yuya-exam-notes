## シナリオ2: Claude Code を使ったコード生成

学習塾向けの授業予約サービスを作る「ミナトクラウド」の開発チーム（12人）は、Claude Code でコードの生成・リファクタリング・デバッグ・文書づくりを進めている。リポジトリは `web/`・`api/`・`mobile/`・`infra/` を持つモノレポで、ルートに CLAUDE.md がある。チームの共通の手順はスラッシュコマンドとスキルにまとめている。作業の大きさに応じて、プランモードと直接実行を使い分けたいと考えている。

**問1** ルートの CLAUDE.md には「インデントはスペース2つ」、`api/CLAUDE.md` には「インデントはタブ」と書かれている。`api/` のファイルを編集させると、スペースになる日とタブになる日がある。最も適切な対応はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="C" data-domain="3" markdown>

- A. 近い階層の CLAUDE.md が上の階層を上書きする前提で、ルート側はそのままにして様子を見る
- B. `api/CLAUDE.md` の該当行を「必ず」で強調し、ルートの指示より優先させる
- C. 2つのファイルは連結して読まれるだけなので、片方を直して矛盾そのものを無くす
- D. ルートの内容を `~/.claude/CLAUDE.md` に移し、プロジェクトの指示より弱くする

</div>

??? success "答えと解説"
    **正解: C。** CLAUDE.md は階層ごとに上書きされるのではなく、連結されて文脈に入る。矛盾する指示は優先順位で解決されないので、自分で矛盾を消す。

    - A: 上書きはされない。すべてが連結されて文脈に入るので、矛盾したままだとどちらかが任意に選ばれる
    - B: 強調しても優先順位の仕組みは無く、矛盾が残る限り揺れは消えない
    - D: ユーザー階層も連結されるだけで弱くはならない。チームの規約がリポジトリから消え、ほかのメンバーに効かなくなる

    根拠: [CLAUDE.md の階層と /memory での確認](../notes/03-claude-code/claude-md-hierarchy.md)

**問2** `api/` と `mobile/` の CLAUDE.md に、同じ「個人情報の扱いの規約」（80行）がそれぞれ書き写されている。先月 `api/` 側だけが改訂され、2つの内容がずれた。`web/` と `infra/` の作業では、この規約は要らない。最も適切な整理はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="B" data-domain="3" markdown>

- A. 規約をルートの CLAUDE.md に移し、どのディレクトリの作業でも同じ規約を読ませる
- B. 規約を1つのファイルにまとめ、使う2つの CLAUDE.md から `@` で取り込む
- C. 規約を `.claude/rules/pii.md` に `paths` を書かずに置き、起動時に読ませる
- D. 2つの CLAUDE.md の先頭に「改訂したら他方も直すこと」と書き、書き写しを続ける

</div>

??? success "答えと解説"
    **正解: B。** 同じ規約を複数の CLAUDE.md に書き写しているなら、1か所に置いて、必要なパッケージの CLAUDE.md からだけ `@path` で取り込む。改訂が1か所で済み、要らない作業では読まれない。

    - A: 要らない `web/` と `infra/` の作業でも毎回読み込まれ、文脈を無駄に使う
    - C: `paths` 無しのルールは起動時に必ず読まれるので、要らない作業でも文脈を使う
    - D: 書き写しを続ける限り、またずれる。1か所に置いて取り込むのが筋

    根拠: [CLAUDE.md のモジュール化](../notes/03-claude-code/claude-md-modularization.md)

**問3** ルートの CLAUDE.md は 350行あり、そのうち 120行は、各サービスの `migrations/` の下の `.sql` を書くときだけ要る規約だ。マイグレーションに触れない作業でも、毎回この 120行が文脈を使っている。文脈の消費を減らす方法として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="A" data-domain="3" markdown>

- A. 120行を、`paths: ["**/migrations/**/*.sql"]` 付きの `.claude/rules/` のルールに移す
- B. 120行を `docs/migrations.md` に移し、ルートの CLAUDE.md から `@docs/migrations.md` で取り込む
- C. 120行を `.claude/rules/migrations.md` に移し、frontmatter に `paths` を書かずに置く
- D. 120行を 30行に要約し直し、ルートの CLAUDE.md に残して、毎回の文脈を小さくする

</div>

??? success "答えと解説"
    **正解: A。** 一部のファイルを扱うときだけ要る規約は、`paths` 付きのルールにすると、合うファイルを扱ったときだけ読み込まれる。import や `paths` 無しのルールに移すだけでは、文脈の量は減らない。

    - B: 取り込んだファイルは取り込み元と一緒に読まれるので、文脈の消費は減らない
    - C: `paths` 無しのルールは起動時に読まれるので、毎回の消費は変わらない
    - D: 減るのは一部だけで、関係ない作業でも読まれ続ける。要約で規約の中身も落ちる

    根拠: [パス指定ルールによる規約の条件付き読み込み](../notes/03-claude-code/path-scoped-rules.md)、[CLAUDE.md のモジュール化](../notes/03-claude-code/claude-md-modularization.md)

**問4** チームは `.claude/skills/release-note/` をリポジトリで共有している。先週チームがこのスキルを改訂したが、ある開発者の環境だけ古い動きのままだ。この開発者は以前、試しに `~/.claude/skills/release-note/` を作っていた。正しい理解と対応はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="A" data-domain="3" markdown>

- A. 同じ名前なら個人のスキルが優先されるので、個人の方を消すか、別の名前に変える
- B. プロジェクトのスキルが個人より優先されるので原因は別にあり、起動し直して様子を見る
- C. 同じ名前のスキルは中身が合わさって動くので、個人の方の手順を改訂に合わせて直す
- D. 個人のスキルは `~/.claude/commands/` に置かないと動かないので、原因は別にある

</div>

??? success "答えと解説"
    **正解: A。** スキルの置き場所が違っても、同じ名前なら個人（`~/.claude/skills/`）の方が優先される。個人用の変種は、チームのスキルと別の名前で作る。

    - B: 優先順位が逆。公式の順位はエンタープライズ > 個人 > プロジェクトで、同じ名前なら個人の方が動く
    - C: 中身は合わさらない。個人の方だけが動くので、直しても改訂の取り込みを毎回手でやることになる
    - D: `~/.claude/skills/` の個人のスキルは動く。動いているからこそ、チームのものを上書きしている

    根拠: [カスタムスラッシュコマンドとスキル](../notes/03-claude-code/slash-commands-and-skills.md)

**問5** 開発者が、依存パッケージを調べる `/dep-audit` スキルに `context: fork` を付けた。スキルの本文は「さっき決めた方針に沿って、依存パッケージを調べて報告して」の1行だけだ。直前の会話で「メジャーバージョンを上げる候補だけを挙げる」と決めていたのに、報告にはすべての更新が並ぶ。最も適切な直し方はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="B" data-domain="3" markdown>

- A. 呼ぶ直前に会話で方針をくり返し、fork したサブエージェントに伝わりやすくする
- B. 方針（メジャーバージョンの更新候補だけ）を、SKILL.md の本文か引数で渡す
- C. `context: fork` を外す。fork するとスキルの本文が読まれなくなるため
- D. `agent: Explore` を足し、会話の履歴を読めるサブエージェントで動かす

</div>

??? success "答えと解説"
    **正解: B。** `context: fork` のスキルは別のサブエージェントの文脈で走り、会話の履歴は渡らない。必要な情報は、すべて SKILL.md と引数に書く。

    - A: fork したサブエージェントは会話の履歴を見ないので、何度くり返しても届かない
    - C: fork でもスキルの本文はサブエージェントへの指示として渡る。問題は本文に方針が無いこと
    - D: Explore も会話の履歴は見ない。`agent` は fork 先の種類を決めるだけ

    根拠: [SKILL.md の frontmatter](../notes/03-claude-code/skill-frontmatter.md)

**問6** 今週の作業のうち、プランモードで調べて計画を立て、承認してから実装すべきものはどれか。（2つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="B,D" data-domain="3" markdown>

- A. 予約確定メールの文面にある誤字を1か所直し、送信のテストも通す
- B. 通知の送り方を自前のキューかマネージドのサービスから選び、3つのサービスを改修する
- C. スタックトレースで特定済みの箇所に、null の確認を1行足して例外を防ぐ
- D. 日付ライブラリを別のものに置き換える（使っている箇所は約70ファイル）
- E. 1つの関数の中だけで使うローカル変数の名前を、意味の分かる名前に変える

</div>

??? success "答えと解説"
    **正解: B と D。** 決め手は設計の判断が要るかどうかと、変更の規模・不確かさだ。方式の選択を含む改修と、多数のファイルに及ぶ置き換えはプランモードで調べてから実装する。原因と範囲の分かった小さな変更は直接実行する。

    - A: 範囲がはっきりした小さな変更。計画を挟むと手間が増えるだけ
    - C: 原因と場所が分かっている1か所の修正なので、直接実行する
    - E: 影響が1つの関数に閉じ、設計の判断も要らない

    根拠: [プランモードと直接実行の使い分け](../notes/03-claude-code/plan-mode-vs-direct.md)

**問7** 授業料の割引計算（兄弟割・早割・回数券の併用）を Claude Code に実装させた。Claude は「実装しました」と答えたが、あとで人が試すと、割引が重なる境目のケースで金額が違った。次の改修から、完成の判定を確実にしたい。最も適切な進め方はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="A" data-domain="3" markdown>

- A. 期待する金額と境目のケースを網羅したテストを先に書き、失敗の出力を返して直させる
- B. 実装のあとに「境目のケースもよく確かめて」と頼み、Claude に自分で確かめさせる
- C. 割引の規則を文章でさらに細かく書き直し、プロンプトの先頭に置く
- D. 実装のたびに人が画面で数件を試し、違った金額を「おかしい」とだけ伝える

</div>

??? success "答えと解説"
    **正解: A。** 「できた」の判定は、先に書いたテストに任せる。期待する動作と境界値を網羅したテストを先に書き、失敗したテストの出力をそのまま返して直させる（テスト駆動の反復）。

    - B: Claude は「できたように見える」ところで止まる。判定できるチェックが無いと、確かめ方も揺れる
    - C: 文章の指示は言い換えても解釈が揺れる。完成の判定にもならない
    - D: 見た目で完成を判断している。「おかしい」だけでは何をどう直すか伝わらない

    根拠: [Claude Code での反復的な改善](../notes/03-claude-code/iterative-refinement.md)

**問8** チームは push の前に走るスクリプトで、Claude Code に変更点の危険な箇所を挙げさせ、スクリプトが `file`・`line`・`severity` を読んで一覧にしている。今は `claude -p "…（JSON で答えて）" --output-format json` で実行し、出力の `result` を JSON として読んでいるが、ときどき読み取りに失敗する。最も適切な直し方はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="D" data-domain="3" markdown>

- A. `--output-format stream-json` に変え、1行ずつ届く JSON を順に読む
- B. プロンプトに「JSON 以外は絶対に出力しないこと」と書き足し、`result` を読み続ける
- C. `--output-format text` に戻し、出力から正規表現で3つの項目を切り出す
- D. `--json-schema` で形を指定し、`structured_output` の有無を確かめて読む

</div>

??? success "答えと解説"
    **正解: D。** 後段のプログラムが読む出力は、`--output-format json` に `--json-schema` を組み合わせて形を固定し、`structured_output` から読む。`structured_output` は無いこともあるので、使う前に有無を確かめる。

    - A: stream-json は進み具合を逐次出す形式で、回答の形を固定する仕組みではない
    - B: `--output-format json` だけではスキーマは強制されず、`result` は文章のまま。頼み方を強めても形は揺れる
    - C: 自由な文章は形が揺れるので、切り出す処理が壊れる

    根拠: [CI での Claude Code の非対話実行と構造化出力](../notes/03-claude-code/ci-non-interactive.md)

**問9** チームは「コミットの前に必ず `npm run lint` を通す」を CLAUDE.md に書いている。ほとんどの場合は守られるが、長い作業の途中で抜けることがある。抜けると困る決まりだ。最も適切な対応はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="C" data-domain="3" markdown>

- A. CLAUDE.md の該当行を先頭に移し、「絶対に」「例外なく」と書き足す
- B. 同じ指示を `.claude/rules/lint.md` に `paths` を書かずに置き、二重に読ませる
- C. CLAUDE.md は強制ではなく文脈なので、コミットの前に lint を走らせるフックを設定する
- D. 同じ指示を各開発者の `~/.claude/CLAUDE.md` にも書き、階層を重ねて効かせる

</div>

??? success "答えと解説"
    **正解: C。** CLAUDE.md はユーザーメッセージとして渡される文脈で、強制する仕組みではない。必ず実行させたいことはフックにする。

    - A: 書き方を強めても文脈であることは変わらず、守られる保証にはならない
    - B: 同じ文脈を2回入れるだけで、強制にはならない
    - D: 階層を重ねても連結されるだけ。新しいメンバーの環境には入らず、ばらつきも増える

    根拠: [CLAUDE.md の階層と /memory での確認](../notes/03-claude-code/claude-md-hierarchy.md)

**問10** 開発者が1つのセッションで、予約の二重登録が起きる原因を2時間調べている。検索結果やログの出力で文脈が埋まってきたが、調査はまだ続ける。ここまでに「`BookingLock` の取得順が原因らしい」と分かっている。最も適切な対応はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="A" data-domain="5" markdown>

- A. `/compact` で、`BookingLock` の発見を焦点に指定して詰める
- B. `/clear` で会話を空にし、分かったことを踏まえて最初から調べ直させる
- C. 何もせずに続け、文脈が溢れたら自動で要約されるのに任せて進める
- D. 「これからは短く答えて」と頼み、以後の出力の量を減らして続ける

</div>

??? success "答えと解説"
    **正解: A。** 同じ調査を続けるなら `/compact <焦点>` で、今後も使う論点を指定して詰める。焦点を指定すれば、残したい発見が要約で落ちにくい。

    - B: `/clear` は無関係な作業に切り替えるときのもの。ここまでの発見を捨てることになる
    - C: 自動の要約では何を残すかをモデルが決めるので、肝心の発見が埋もれうる
    - D: すでに埋まった文脈は減らず、検索やログの出力もそのまま積まれる

    根拠: [大きなコードベースの探索でのコンテキスト管理](../notes/05-context-reliability/large-codebase-context.md)

**問11** ある開発者が、調べ終えたセッションから `--fork-session` で2つの枝を作り、同じ作業ディレクトリで、片方に「キャッシュで速くする案」、もう片方に「クエリを直す案」を同時に実装させた。すると、片方の枝の変更が、もう片方の枝のテスト結果に混ざった。原因と対応として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="B" data-domain="1" markdown>

- A. フォークは元のセッションも書き換えるので、`--continue` で元を開き直してから試す
- B. フォークで分かれるのは会話だけでファイルは共有されるので、枝ごとに別のブランチや作業ツリーで試す
- C. フォークでは会話の履歴が渡らないので、各枝に調査結果を貼り直してから試す
- D. フォークの枝は同時に動かせないので、片方が終わってから、もう片方を再開する

</div>

??? success "答えと解説"
    **正解: B。** 再開もフォークも扱うのは会話だけで、ファイルの状態は分かれない。枝どうしが同じファイルを書き換えると干渉するので、別のブランチや作業ツリーで試す。

    - A: フォークは元を変えない（新しい ID の枝ができる）。問題はファイルが共有されていること
    - C: フォークは会話の写しを持つ。履歴が渡らないのは普通のサブエージェントの話
    - D: 同時に動かせる。順に動かしても、同じディレクトリを書き換えれば前の枝の変更が残る

    根拠: [セッションの再開とフォーク](../notes/01-agentic-architecture/session-resume-fork.md)

**問12** 開発者は、決済の不具合と通知の遅延の2つの調査を、別々のセッションで並行して進めている。翌朝、決済の調査を続けようと `claude --continue` で開くと、通知の調査が開いた。今後のやり方として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="C" data-domain="1" markdown>

- A. 毎朝、前日の調査の要約を手で書き、新しいセッションに貼って始める
- B. `--continue` に `--fork-session` を足し、直近のセッションから枝を作って開く
- C. 各セッションに名前を付けておき、`claude --resume <名前>` で目的のセッションを開く
- D. 2つの調査を1つのセッションにまとめ、`--continue` で開けば必ず同じ調査が出るようにする

</div>

??? success "答えと解説"
    **正解: C。** `--continue` は直近の1つを開く。複数の調査を並行しているなら、名前（または ID）で `--resume` する。

    - A: 前の文脈がまだ有効なら、要約し直さずに再開すればよい。手間が増え、要約で情報も落ちる
