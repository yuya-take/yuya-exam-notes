# CLAUDE.md の階層（ユーザー / プロジェクト / ディレクトリ）と /memory での確認

> ドメイン: 3. Claude Code の設定とワークフロー（20%） ／ 更新: 2026-11-20

## 3行まとめ
- CLAUDE.md（毎セッション読み込まれる指示のファイル）は、ユーザー・プロジェクト・ディレクトリの3階層に置ける。置き場所で「誰に効くか」が決まる
- チーム全員に効かせる規約はプロジェクト（バージョン管理に入る）、自分だけの好みはユーザー（`~/.claude/CLAUDE.md`）に書く
- 「人によって・セッションによって挙動が違う」ときは、まずどのファイルが読み込まれているかを `/memory` などで確かめる

## 仕組み

### 階層ごとの置き場所・共有範囲・読み込まれ方

| 階層 | 置き場所 | 共有範囲 | 読み込まれ方 |
|---|---|---|---|
| ユーザー（user-level） | `~/.claude/CLAUDE.md` | 自分だけ（全プロジェクト）。リポジトリに入らない | 起動時 |
| プロジェクト（project-level） | `./CLAUDE.md` または `./.claude/CLAUDE.md` | チーム全員（バージョン管理で共有） | 起動時 |
| ディレクトリ（directory-level） | サブディレクトリの `CLAUDE.md` | チーム全員（リポジトリに入れた場合） | そのサブディレクトリのファイルを読む・書くときに、必要になってから |

- 起動したディレクトリより上にある CLAUDE.md は、起動時に読み込まれる
- 公式ドキュメントには、ほかに組織全体の managed policy（IT 部門が配る、除外できない CLAUDE.md）と、`./CLAUDE.local.md`（自分だけのプロジェクト用。`.gitignore` に入れる）もある

### 読み込みの順序

```mermaid
flowchart LR
  M[managed policy] --> U[ユーザー<br>~/.claude/CLAUDE.md] --> P[プロジェクト<br>./CLAUDE.md] --> D[サブディレクトリの<br>CLAUDE.md<br>必要になってから]
```

- 上書きではなく、すべて連結されて文脈に入る。後ろ（作業場所に近い方）ほど後に読まれる
- 矛盾する指示があると、Claude はどちらかを任意に選ぶことがある。優先順位で解決される仕組みではない

### 確かめ方

| やりたいこと | 使うもの |
|---|---|
| メモリファイルの一覧を見て、開いて直す | `/memory` |
| 起動時に読み込まれたファイルを確かめる | `/context all` の Memory files の一覧 |
| いつ・なぜ読み込まれたかを記録する | `InstructionsLoaded` フック |

### 分割の仕組み（概要だけ）
- `@path` の import と `.claude/rules/` で CLAUDE.md を分ける → 別ノート（CLAUDE.md のモジュール化）
- `paths` で特定のファイルだけに効かせるルール → 別ノート（3.3 のパス指定ルール）

## 試験で問われそうなポイント
- 新しく入ったメンバーに規約が効かない → 規約がユーザー階層にあると疑い、プロジェクトの CLAUDE.md に移す
- 個人の好み（エディタ流儀、口調など）→ ユーザー階層か `CLAUDE.local.md`。チームのリポジトリには入れない
- 一部のディレクトリだけの規約 → そのサブディレクトリの CLAUDE.md（複数ディレクトリにまたがるなら 3.3 のパス指定ルール）
- セッションごとに挙動が違う → 読み込まれたメモリファイルを確かめてから直す。プロンプトを足して様子を見るより先にやる

## 間違えやすいところ
- アンチパターン: チーム全員に効かせたい規約を、自分の `~/.claude/CLAUDE.md` に書く。自分の環境では効くので気づきにくい
- ユーザー階層の `~/.claude/CLAUDE.md` とプロジェクトの `./.claude/CLAUDE.md` は名前が似ているが、共有範囲が逆
- サブディレクトリの CLAUDE.md は起動時には読み込まれない。`/context all` の一覧に出なくても異常ではない
- 「下の階層が上を上書きする」わけではない。連結されるだけなので、矛盾は自分で消す
- CLAUDE.md は強制ではなく文脈（ユーザーメッセージとして渡される）。必ず実行させたいことはフック（hook）にする
- ガイドとのずれ: ガイドは「`/memory` で読み込まれたファイルを確かめる」と書く。現行の公式ドキュメントでは `/memory` は存在しないファイルも含めて一覧・編集する画面で、読み込みの確認は `/context all` が主。試験ではガイドの書き方（`/memory`）で答える

## 確認問題
1. 開発者 A のマシンでは「コミット前に lint を通す」が守られるが、先週入った B のマシンでは守られない。リポジトリの CLAUDE.md にはその記述が無い。まず何を疑い、どう直すか。
   <details><summary>答え</summary>A の `~/.claude/CLAUDE.md`（ユーザー階層）に書かれていると疑う。ユーザー階層はバージョン管理で共有されない。プロジェクトの `./CLAUDE.md` に移してコミットする。必ず守らせたいならフックも検討する。</details>
2. モノレポの `services/billing/` だけで使う命名規則がある。ルートの CLAUDE.md に書くと、ほかのチームの作業でも毎回文脈を使う。どこに書くか。
   <details><summary>答え</summary>`services/billing/CLAUDE.md`（ディレクトリ階層）。そのディレクトリのファイルを扱うときだけ読み込まれる。同じ規則が複数のディレクトリに散らばるファイルに効くなら、3.3 のパス指定ルールを選ぶ。</details>
3. 同じリポジトリで、昨日と今日で Claude の振る舞いが違う。設定を変えた覚えはない。最初の一手は何か。
   <details><summary>答え</summary>`/memory`（現行のドキュメントでは `/context all` も）で、どのメモリファイルが読み込まれているかを確かめる。起動したディレクトリの違いや、サブディレクトリの CLAUDE.md の読み込み有無で中身が変わっていることがある。</details>
