# エンドツーエンドの構成の評価

> ドメイン: 1. ソリューションの設計とアーキテクチャ（18%） ／ 更新: 2026-11-26

!!! abstract "ひとことで"
    構成は「入力 → 処理 → 出力 → フィードバック」の段ごとに、拡張性・保守性・アクセス制御の要件と突き合わせる。負荷や信頼の条件を1つ与えられたら、==その条件で最初に壊れる部品==を1つ特定し、そこを直す。

## 仕組み

評価では、要件を段に割り当ててから、条件をかけて壊れる順を考える。負荷の条件なら、処理の容量がどこで先に尽きるかを見る。信頼の条件なら、信頼できない入力や他人のデータが、どの段から入って何に届くかを見る。直すのは最初に壊れる部品であり、まだ余裕のある部品を強くしても結果は変わらない。

```mermaid
flowchart LR
  I[入力: 利用者の依頼・取り込む文書] --> P[処理: 検索・モデル呼び出し・ツール]
  P --> O[出力: 回答・更新・通知]
  O --> F[フィードバック: ログ・評価・改善]
  F --> P
  classDef run fill:#e3f2fd,stroke:#1e88e5,color:#0d47a1
  classDef judge fill:#fff8e1,stroke:#f9a825,color:#4e342e
  class I,O,F run
  class P judge
```

| 条件 | 最初に壊れやすい部品 | 見るべき証拠 |
|---|---|---|
| 同時実行が増える | 自前ホストの Agent SDK。1セッションが1つのサブプロセスで、ホストのメモリが同時数の上限になる | メモリ使用量、プロセスの強制終了。API の 429 が出ていないこと |
| 呼び出し量が増える | API のレート制限（利用の階層ごとに決まる） | 429 の比率。メモリやキューに余裕があること |
| 取り込む文書が信頼できない | ツールの権限とネットワークの範囲。注入された指示は、届く範囲すべてに作用する | エージェントが使える認証情報と、到達できるホスト |
| 1つの環境を複数の顧客で共有する | 設定とメモリのファイル。既定では、ファイルシステムの設定と `CLAUDE.md` を読む | 他の顧客の文脈が回答に混ざる |

アクセス制御は、モデルに渡す前の段で効かせる。検索結果を依頼者の権限で絞らずに渡せば、プロンプトで「見せるな」と書いても漏れうる（推論）。Managed Agents の公式ドキュメントも、==モデルのふるまいはセキュリティの制御ではない==と書き、ネットワーク設定と権限ポリシーで縛るよう求めている。

保守性は、何を版で管理できるかで差が出る。Managed Agents では、エージェントの定義は版を持ち、セッションを特定の版に固定できる。一方で環境（environment）は版を持たないので、変更の記録は自分で残す。

??? info "数値と仕様の細部"
    - Agent SDK の自前ホストでは、1エージェントあたり RAM 1 GiB・ディスク 5 GiB・CPU 1 が出発点。セッションが長いほどメモリは増える。ホストあたりの数は「(RAM − オーバーヘッド) ÷ 1セッションの上限」で見積もる
    - Agent SDK の既定では、セッションの記録はコンテナのローカルディスクにあり、再起動や縮退で消える。残すには `SessionStore` を使う
    - 共有コンテナで顧客を分けるには、`settingSources: []`（Python は `setting_sources=[]`）、`CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`、顧客ごとの `CLAUDE_CONFIG_DIR` と `cwd`、顧客ごとの外向き通信の規則を組み合わせる
    - Managed Agents の `limited` ネットワークでも、許可したホストへは書き込み（`git push` など）を含めて何でも送れる。許可はホスト単位で、操作単位ではない

## 試験での見分け方

<div class="vs" markdown>

| 問われること | ○ 正しい | × ひっかけ |
|---|---|---|
| 負荷で落ちる原因 | ログで、尽きている資源を特定してから直す | 証拠の無い部品（レート制限の階層、モデル）を先に替える |
| 文書の権限を守る | 依頼者の権限で検索結果を絞ってからモデルに渡す | システムプロンプトで「権限の無い文書は使うな」と指示する |
| 信頼できない入力 | ツールの権限と到達先を最小にする | 注入をモデルが見抜くことに頼る |
| 構成の変更を追いたい | 版のある部品は版に固定し、版の無い部品は変更記録を残す | 最新の定義を常に使い、どの設定で動いたかを記録しない |

</div>

## 確認問題

**Q1.** 社内ナレッジ検索のエージェントを、Agent SDK でコンテナに自前で載せている。1コンテナ（RAM 8 GiB）が複数のセッションを長時間受け持つ構成だ。利用者が増えてから、応答の途中でセッションが切れる。運用ログは次のとおり。最初に手を入れるべき箇所はどれか。（1つ選べ）
{ .quiz-q }

```text
host=ks-03 active_sessions=11 rss_total=7.6GiB  OOMKilled pid=4127
host=ks-03 api_status 200=98.9% 429=0.0% 5xx=1.1%
queue_wait_p95=0.4s
```

<div class="quiz" data-answer="C" markdown>

- A. API の利用の階層を上げて、レート制限を広げる
- B. モデルを軽い階層に替えて、1回の呼び出しを速くする
- C. 1ホストに載せるセッション数を、メモリで決まる上限に抑え、ホストを足して振り分ける
- D. プロンプトキャッシュを入れて、入力トークンを減らす

</div>

??? success "答えと解説"
    **正解: C。** 429 は出ておらず、メモリが尽きてプロセスが落ちている。1セッションが1プロセスなので、同時数の上限はホストのメモリで決まる。

    - A: 429 は 0% で、レート制限はまだ効いていない
    - B: 呼び出しの速さはメモリの不足と関係が無い
    - D: 入力トークンが減っても、プロセスのメモリは減らない

**Q2.** 複数の顧客企業に提供する SaaS で、Agent SDK の1つのコンテナが複数の顧客のセッションを受け持つ。ある顧客の回答に、別の顧客の社内規程の内容が混ざった。どの顧客も自分用の `CLAUDE.md` を持っている。最も適切な対策はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="A" markdown>

- A. 設定の読み込み元を空にし、自動メモリを止め、顧客ごとに設定ディレクトリと作業ディレクトリを分ける
- B. システムプロンプトに「他の顧客の情報を回答に使わないこと」と書き足す
- C. 回答を返す前に、別の顧客の社名が含まれていないかを文字列で確かめて止める
- D. 顧客ごとにモデルの階層を分けて、文脈が混ざりにくくする

</div>

??? success "答えと解説"
    **正解: A。** Agent SDK は既定でファイルシステムの設定と `CLAUDE.md` を読む。共有コンテナでは、読み込む元を顧客ごとに分けて断つ。

    - B: 混ざった文脈は、指示の前にもうモデルに入っている
    - C: 社名を含まない形で漏れたものは止められない
    - D: モデルの階層は、どのファイルを読むかと関係が無い

**Q3.** 法律事務所が、所内文書を検索して答えるエージェントを作る。要件は「所員は、自分に閲覧権限のある案件の文書だけを根拠にできる」こと。この要件を満たす設計として適切なものはどれか。（2つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="B,E" markdown>

- A. 検索は全文書を対象にし、システムプロンプトで「権限の無い案件には触れない」と指示する
- B. 検索ツールが、依頼した所員の権限で結果を絞ってからモデルに返す
- C. 回答の後で、案件番号が含まれていないかを文字列で調べて伏せる
- D. 漏れのない回答のため、エージェントには全案件を読める管理者の認証情報を渡す
- E. 検索ツールの呼び出しを、共有の管理者アカウントでなく、依頼した所員の権限で行う

</div>

??? success "答えと解説"
    **正解: B と E。** アクセス制御は、モデルに渡す前の段で効かせる。モデルのふるまいはセキュリティの制御ではない。

    - A: 権限の無い文書がすでに文脈に入っており、指示は歯止めにならない
    - C: 番号を含まない言い換えで漏れたものは防げない
    - D: エージェントの権限を最大にすると、注入や誤りの被害も最大になる
