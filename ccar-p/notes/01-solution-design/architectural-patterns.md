# 構成パターンの選択

> ドメイン: 1. ソリューションの設計とアーキテクチャ（18%） ／ 更新: 2026-11-26

!!! abstract "ひとことで"
    パターンの違いは、==次に何をするかを誰が決めるか==（委任の境界）にある。手順が決まっていて監査で同じ手順を求められるならワークフロー、手順が読めないならエージェント、1回の呼び出しで済むなら拡張 LLM、同じ手順を多くの場面で使い回すなら Skills にする。

## 仕組み

どのパターンも、土台は検索・ツール・メモリを足した LLM（augmented LLM）だ。そこから、制御の流れをコードが持つか、モデルが持つかで分かれる。ワークフローは、決めたコードの道筋に沿って LLM とツールを動かす。エージェントは、モデルが自分で手順とツールの使い方を決める。Anthropic のブログは、最も単純な解から始め、必要なときだけ複雑にすることを勧めている。エージェント型は、遅延とコストを払って性能を得る構成だからだ。

| パターン | 次の一手を決めるのは | 向く条件 | 向かない条件 |
|---|---|---|---|
| 拡張 LLM | アプリのコード（モデルは1回の呼び出しの中だけ） | 検索して答えるなど、1往復で済む | 何段も調べ直す必要がある |
| ワークフロー | コード（連鎖・振り分け・並列・評価と改善の繰り返しなど） | 手順が固定。予測しやすさと監査が要る | 必要な手順の数が読めない |
| エージェント | モデル（ツールと権限の範囲の中で） | 手順の数を事前に決められない開かれた問題 | 毎回同じ手順で、誤りの代償が大きい |
| Skills ベース | 手順はスキルに書き、どのスキルを使うかはモデル | 同じ手順・社内ルールを多くの場面で使い回し、一か所で管理したい | 1回限りの指示。信頼できない出所のスキル |

==Skills は、使い回しと管理の単位==になる。スキルの名前と説明だけが常に文脈に入り、本文と付属ファイルは使うときだけ読み込まれる（段階的な開示、progressive disclosure）。だから多くのスキルを入れても文脈を圧迫しにくい。Claude API にアップロードしたスキルはワークスペースの全員が使え、Claude Code ではプロジェクトの `.claude/skills/` やプラグインで共有する。

リスクの高い業務でエージェントを選ぶなら、サンドボックス・停止条件・人の確認点をセットにする。リスクの高さだけでワークフローに決めるわけではない。手順を事前に決められない作業を無理に固定すると、想定外の入力で詰まる（推論）。

??? info "Skills の細かい決まり"
    - 読み込みの3段階: メタデータ（1スキル約100トークン、常に）→ `SKILL.md` の本文（使うとき、5k トークン未満）→ 付属ファイル（必要なときだけ。スクリプトは出力だけが文脈に入る）
    - Claude API で使うには、コード実行ツール（code execution）のコンテナが要る。API 上のスキルはネットワークに出られず、実行中にパッケージを足せない
    - 独自のスキルは、claude.ai・API・Claude Code の間で同期されない。使う場所ごとに入れる
    - 信頼できる出所（自作か Anthropic）のスキルだけを使う。悪意のあるスキルは、説明と違うツール呼び出しやデータの持ち出しを指示できる
    - Amazon Bedrock、Google Cloud の Google 管理版、Microsoft Foundry の Azure ホスト版では Agent Skills が使えない（[デプロイ先と実行環境の選択](deployment-surface-runtime.md)）

## 試験での見分け方

<div class="vs" markdown>

| 問われること | ○ 正しい | × ひっかけ |
|---|---|---|
| 監査で毎回同じ手順を求められる | コードが道筋を持つワークフロー | 柔軟だからとエージェントに任せる |
| 調べる回数が読めない調査・修正 | エージェント＋停止条件・サンドボックス | 分岐を全部コードで書き尽くそうとする |
| 1回の検索と回答で足りる | 拡張 LLM（検索ツール付きの1回の呼び出し） | マルチエージェントや自律ループを組む |
| 同じ社内手順を多くのチームが使う | スキルにして一か所で版を管理する | 各チームのシステムプロンプトに写して配る |

</div>

## 確認問題

**Q1.** 損害保険会社が、事故報告書から「受付 → 項目の抽出 → 規程との照合 → 担当部署への振り分け」を行う仕組みを作る。手順は毎回同じで、監査部門は「どの書類も同じ手順を通ったことを示す記録」を求めている。最も適切なパターンはどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="A" markdown>

- A. 各段をコードでつなぐワークフローにし、段ごとの入出力を記録する
- B. 1つのエージェントに全ツールを渡し、手順はモデルに任せて結果だけを記録する
- C. 段ごとにサブエージェントを置き、コーディネーターに呼ぶ順番を毎回決めさせる
- D. 手順をスキルに書き、どの段を実行するかをモデルに選ばせる

</div>

??? success "答えと解説"
    **正解: A。** 手順が固定で、同じ手順を通った証拠が要るので、制御の流れをコードが持つワークフローにする。

    - B: 手順をモデルが決めるので、毎回同じ手順を通る保証が無い
    - C: 順番を毎回モデルが決める点は B と同じで、構成も重くなる
    - D: スキルは使い回しの単位で、段の実行順は保証しない

**Q2.** 小売企業の 30 のチームが、同じワークスペースで、それぞれの Claude API アプリのシステムプロンプトに、同じ「商品説明文の社内表記ルール」を写して使っている。ルールの改訂が一部のチームに反映されず、表記がばらつく。最も適切な対応はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="D" markdown>

- A. 改訂のたびに、全チームへシステムプロンプトの差し替えを依頼する
- B. 表記ルールの全文を、全アプリのユーザーメッセージの先頭に毎回付ける
- C. チームごとに表記ルール専用のエージェントを作り、各アプリから呼ばせる
- D. 表記ルールをスキルにしてワークスペースにアップロードし、各アプリから参照させる

</div>

??? success "答えと解説"
    **正解: D。** 使い回す手順はスキルにして一か所で管理する。API のスキルは、アップロードしたワークスペースの全員が使える。

    - A: 写しを配る構造が変わらず、反映漏れが再び起きる
    - B: 写しの数が増えるだけで、改訂の反映先は一つにならない
    - C: チームごとに作れば、定義がまた 30 個に分かれる

**Q3.** パターンの選び方の説明として正しいものはどれか。（2つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="C,D" markdown>

- A. エージェント型は手順が固定の作業でも精度が上がるので、遅延とコストを気にしないなら常に選ぶ
- B. Skills ベースにすると、モデルはツールを呼べなくなり、手順の記述だけに従う
- C. 社内 FAQ を1回検索して答えるだけの窓口なら、検索ツール付きの1回の呼び出しで足りる
- D. 再現手順が分からない不具合の調査は、サンドボックスと停止条件を付けたエージェントに向く
- E. ワークフローでは、次にどの段を実行するかをモデルが毎回決める

</div>

??? success "答えと解説"
    **正解: C と D。** 1往復で済むなら拡張 LLM、手順が読めないならエージェントにする。

    - A: 最も単純な解から始め、必要なときだけ複雑にする。手順が固定ならワークフローの方が予測しやすい
    - B: スキルは手順や付属スクリプトを渡す仕組みで、ツールの利用を止めない
    - E: ワークフローは、コードが決めた道筋で進む
