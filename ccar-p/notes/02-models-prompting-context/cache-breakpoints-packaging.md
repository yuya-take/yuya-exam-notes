# キャッシュのブレークポイントと再利用できる形

> ドメイン: 2. モデル・プロンプト・コンテキストエンジニアリング（13%） ／ 更新: 2026-11-26

!!! abstract "ひとことで"
    呼び出しの間で==変わらないものを前に、変わるものを後ろに==並べ、ブレークポイントは「毎回同じ最後のブロック」に置く。たまにしか使わない手順書は Skills にして、使うときだけ読ませる。

## 仕組み

キャッシュは、リクエストの先頭からブレークポイントまでの接頭辞が完全に一致したときに当たる。接頭辞は tools → system → messages の順に組まれる。途中の1か所が変われば、そこから後ろはすべて当たらない。だから、並べる順番がキャッシュの効き目を決める。日付やユーザー名のような毎回変わる値が前にあると、後ろの大きな固定部分まで巻き添えで外れる。

ブレークポイントは1リクエストに最大4つ置ける。共通の部分と、テナントや仕事の種類ごとの部分があるなら、共通部分の末尾に1つ、種類別の部分の末尾にもう1つ置く。こうすると、種類が変わっても共通部分は当たり続ける。

```mermaid
flowchart LR
  A[tools<br>固定] --> B[system 共通の指示<br>BP1]
  B --> C[テナント別の用語集<br>BP2]
  C --> D[会話の履歴<br>BP3 か自動]
  D --> E[今回の質問<br>キャッシュしない]
  classDef run fill:#e3f2fd,stroke:#1e88e5,color:#0d47a1
  classDef done fill:#e8f5e9,stroke:#43a047,color:#1b5e20
  class A,B,C done
  class D,E run
```

| 変えたもの | tools のキャッシュ | system のキャッシュ | messages のキャッシュ |
|---|---|---|---|
| ツール定義（名前・説明・引数） | 外れる | 外れる | 外れる |
| `tool_choice` | 当たる | 当たる | 外れる |
| 画像の追加・削除 | 当たる | 当たる | 外れる |
| thinking の設定、トップレベルの `effort` | モデルによる | モデルによる | 外れる |
| Skills の一覧（container.skills） | 未確認 | 外れる（Skills は system に入る） | 外れる |

手順書の束は、Agent Skills にすると段階的に読み込まれる（progressive disclosure）。常に載るのは名前と説明だけで、本文の `SKILL.md` は使うと判断されたときに読まれる。付属のファイルは読まれるまでトークンを消費しない。スクリプトは実行され、出力だけがコンテキストに入る。Skills は system に固定の順で入るので、一覧と順番を毎回そろえればキャッシュも当たる。

??? info "数字と細かい決まり（2026-11-26 に公式で確認）"
    - 単価の倍率: 5分キャッシュの書き込み 1.25 倍、1時間の書き込み 2 倍、読み込み 0.1 倍（Opus 5.5・Sonnet 5.5 は 0.05 倍、Fable 5.2 は 0.025 倍）。5分なら1回、1時間なら2回読めば元が取れる
    - TTL の既定は5分で、読まれるたびに延びる。1時間は `"ttl": "1h"`。混ぜるときは1時間のものを前に置く
    - キャッシュできる最小の長さ: 5.x 世代は 512 トークン。Opus 4.6／4.5・Haiku 4.5 は 4,096。短いとエラーなしで素通りするので、`usage` で確かめる
    - 書き込みはブレークポイントでだけ起きる。当たりを探すのは、ブレークポイントから最大20ブロック前まで。会話が伸びて20ブロックを超えそうなら、手前にもう1つ置く
    - 自動キャッシュ（トップレベルの `cache_control`）は最後のブロックに置かれる。最後が毎回変わるなら、固定部分の末尾に明示のブレークポイントを置く。Bedrock の bedrock-runtime では自動キャッシュが使えない
    - 同時に送ったリクエストは、最初の応答が始まるまで互いのキャッシュを使えない。最初の応答を待ってから並列に送る。`max_tokens: 0` で事前に書き込む方法もある
    - キャッシュは組織ごと、Claude API ではワークスペースごとに分かれる
    - Skills: メタデータは1つ約 100 トークン、`SKILL.md` 本文は 5k トークン未満が目安。1リクエストに最大20個。API ではコード実行ツールが要る。本番ではバージョンを固定する。`latest` だと、新しい版で説明文が変わったときにキャッシュが外れうる
    - Agent Skills は ZDR の対象外

## 試験での見分け方

<div class="vs" markdown>

| 問われること | ○ 正しい | × ひっかけ |
|---|---|---|
| 書き込みばかりで読み込みが0 | 変わる値（時刻・ユーザー名）を固定部分の後ろへ移す | TTL を1時間に延ばす（毎回変わる限り当たらない） |
| 共通部分と種類別の部分がある | 共通を先に置いて BP、種類別の後ろにもう1つ BP | 種類別を先に置き、末尾に1つだけ置く |
| ブレークポイントの位置 | 毎回同じ最後のブロック | ユーザーのメッセージや、毎回変わるブロック |
| たまにしか使わない手順書 | Skills にして、使うときだけ読ませる | 全部を system に貼る、全部をツールの説明に書く |
| Skills とキャッシュ | 一覧と順番をそろえ、本番は版を固定する | リクエストごとに一覧を組み替える、`latest` を使う |

</div>

## 確認問題

**Q1.** 社内規程に答えるアシスタントの system は次のとおりで、`usage` は毎回 `cache_creation_input_tokens: 40210`、`cache_read_input_tokens: 0` を示す。原因と直し方として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

```json
"system": [
  {"type": "text", "text": "現在時刻: 2026-11-26T14:03:22+09:00"},
  {"type": "text", "text": "<社内規程 約4万トークン>",
   "cache_control": {"type": "ephemeral"}}
]
```

<div class="quiz" data-answer="B" markdown>

- A. TTL が短すぎるので、`"ttl": "1h"` にして書き込んだ内容を長く残す
- B. 毎回変わる時刻が接頭辞の先頭にあるので、規程の後ろ（user メッセージなど）へ移す
- C. ブレークポイントが足りないので、時刻のブロックにも `cache_control` を付ける
- D. 明示の指定をやめ、トップレベルの自動キャッシュに任せる

</div>

??? success "答えと解説"
    **正解: B。** 接頭辞の先頭が毎回変わるので、後ろの規程も一致しない。固定部分を前に出せば当たる。

    - A: 時刻が変わる限り接頭辞は一致せず、書き込みが2倍の単価になるだけだ
    - C: 時刻のブロックで書き込んでも、次の時刻とは一致しない
    - D: 自動キャッシュも接頭辞の一致が前提で、時刻が先頭にある限り当たらない

**Q2.** 300テナントの SaaS で、共通の指示 20,000 トークン、テナント別の用語集 6,000 トークン、会話の履歴の順に送っている。今は「用語集 → 共通の指示」の順で、末尾に1つだけブレークポイントがある。利用の少ないテナントで、ヒット率が特に低い。最も適切な対応はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="D" markdown>

- A. 300テナント分の用語集をすべて1つの system にまとめ、全テナントで同じ接頭辞にする
- B. 並びはそのままで TTL を1時間にし、利用の少ないテナントでも残るようにする
- C. テナントごとに別のワークスペースを使い、キャッシュが混ざらないようにする
- D. 共通の指示を先に置いてその末尾にブレークポイントを置き、用語集の末尾にもう1つ置く

</div>

??? success "答えと解説"
    **正解: D。** 共通の 20,000 トークンが全テナントで同じ接頭辞になり、利用の少ないテナントでも共通部分は当たる。

    - A: 6,000 × 300 で約 180 万トークンになり、コンテキストに収まらない
    - B: 共通部分がテナントごとに別の接頭辞のままで、書き込みの単価も2倍になる
    - C: キャッシュはワークスペースごとに分かれるので、共通部分まで共有できなくなる

**Q3.** API で動くデータ分析エージェントの system に、12本の手順書（1本 3,000〜8,000 トークン）を貼っている。1回の作業で使うのは1〜2本で、手順書は毎週どれかが直される。再利用の形として適切なものはどれか。（2つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="A,B" markdown>

- A. 手順書を1本ずつカスタム Skill にし、名前と説明だけを常に載せて本文は使うときに読ませる
- B. 本番では Skill の版を固定し、container.skills の一覧と順番を毎回そろえる
- C. 手順書は毎回 user メッセージの先頭に貼り直し、system を短く保つ
- D. Skill の版は `latest` にして、週ごとの修正がすぐ本番に入るようにする
- E. 手順書の中身をツールの description に書き移し、ツールとして毎回載せる

</div>

??? success "答えと解説"
    **正解: A と B。** 段階的な読み込みで量を減らし、一覧と版を固定して接頭辞を安定させる。

    - C: 毎回の入力の量は減らず、キャッシュの位置も不安定になる
    - D: 誰かが版を上げるたびに本番の振る舞いが変わる。説明文が変わればキャッシュも外れる
    - E: ツールの定義は毎回すべて載るので、量は減らない
