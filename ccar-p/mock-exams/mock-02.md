## 問1〜15

**問1** 物流のアサギ運輸で、配送伝票の不備を分類する仕組みのモデル構成を見直している。要件は「社内の評価セット 1,200 件で正答率 95% 以上」「p95 3 秒以内」「月額 $2,500 以内」。今期の経営が掲げた価値の柱は「ソリューションのコスト」で、要件を満たしたまま月額を下げることを求めている。評価の結果は次のとおり。最も適切な構成はどれか。（1つ選べ）
{ .quiz-q }

| 構成 | 正答率 | p95 | 月額の見込み |
|---|---|---|---|
| Opus 5.5 / `medium`（現行） | 98.1% | 2.6 秒 | $2,400 |
| Sonnet 5.5 / `medium` | 97.4% | 1.9 秒 | $1,300 |
| Sonnet 5.5 / `low` | 95.6% | 1.4 秒 | $900 |
| Haiku 5.5 / `medium` | 93.8% | 0.8 秒 | $150 |

<div class="quiz" data-answer="D" data-domain="1" markdown>

- A. 正答率が最も高い Opus 5.5 / `medium` を続け、予算の残りで正答率をさらに上げる
- B. 最も速く安い Haiku 5.5 / `medium` に替え、足りない正答率は後からプロンプトで補う
- C. 正答率と速さの釣り合いが良い Sonnet 5.5 / `medium` に替える
- D. 要件をすべて満たす中で最も安い Sonnet 5.5 / `low` に替える

</div>

??? success "答えと解説"
    **正解: D。** まず上限（正答率・p95・月額）を破る案を外し、残りを問われた柱で比べる。柱が「ソリューションのコスト」なので、要件を満たす中で最も安い案が勝つ。

    - A: 要件の上で品質を伸ばしても、問われた柱（コスト）は伸びない。現行のままでは月額も下がらない
    - B: 正答率 93.8% は要件を割る。評価で確かめていない「後から補う」は、上限で外す段を飛ばしている
    - C: 要件は満たすが、同じ要件を満たすより安い案（$900）がある。釣り合いは問われた柱ではない

    根拠: [価値にもとづく設計の判断](../notes/01-solution-design/value-based-decisions.md)

**問2** 社内の開発基盤チームが、Claude Code のサブエージェント `build-runner` を配っている。役割はビルドとテストの実行で、`Bash` が要る。誤ってファイルを消す事故を防ぐため、frontmatter に `disallowedTools` の1行を足したところ、`build-runner` がビルドのコマンドをまったく実行できなくなった。「Bash は残し、`rm` だけを止める」という目的に合う直し方として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

```yaml
---
name: build-runner
description: ビルドとテストを実行し、失敗の要約を返す
tools: Read, Grep, Glob, Bash
disallowedTools: Bash(rm *)
---
```

<div class="quiz" data-answer="C" data-domain="3" markdown>

- A. `disallowedTools` を `Bash(rm -rf *)` に狭め、ほかの形の `rm` は通すことにする
- B. `disallowedTools` を外し、サブエージェントの本文に「rm は使わないこと」と書く
- C. frontmatter の `disallowedTools` を外し、settings の `permissions.deny` に `Bash(rm *)` を書く
- D. `tools` から `Bash` を外し、ビルドの実行は親のエージェントに頼むようにする

</div>

??? success "答えと解説"
    **正解: C。** サブエージェントの frontmatter の `disallowedTools` に `Bash(rm *)` と書くと、Bash ツールごと外れる。Bash を残して特定のコマンドだけ止めるなら、settings の `permissions.deny` に書く。

    - A: パターンを狭めても、frontmatter に書く限り Bash ツールごと外れる症状は変わらない
    - B: 本文の指示は強制にならない。見えているツールは誤った判断で呼ばれうる
    - D: 役割に要る Bash を失い、ビルドとテストを任せるという分担そのものが崩れる

    根拠: [最小権限のツール構成](../notes/03-integration/least-privilege-tools.md)

**問3** 医療機器メーカーのサポート窓口で、問い合わせの記録と添付の点検記録をまとめて読ませ、不具合の報告を8つの型に振り分ける。評価で品質の下限を満たした Haiku 5.5 を選び、月額の上限 $3,000 に対して、1件の入力を約 120,000 トークン（キャッシュの読み込みを含む）として、Haiku 5.5 の基本の単価で見積もった。ところが初月の請求は、見積もりの約5倍だった。件数と1件あたりのトークン数は見積もりどおりだった。最も適切な対応はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="D" data-domain="2" markdown>

- A. キャッシュの TTL を1時間に延ばし、読み込みの割合を上げて費用を見積もりに近づける
- B. 見積もりに thinking のトークンを入力として足していなかったので、入力の単価で足し直す
- C. fast mode をやめ、割増の単価が付かない通常の速度で動かすように切り替える
- D. プロンプトが 100,000 トークンを超えるリクエストは高い単価になるので、その単価で見積もり直して上限と比べる

</div>

??? success "答えと解説"
    **正解: D。** Haiku 5.5 は、キャッシュの読み込みも含めたプロンプトが 100,000 トークンを超えると、そのリクエストは高い単価（入力・出力とも約5倍）になる。件数とトークン数が見積もりどおりなら、単価の前提が違う。その単価で見積もり直し、上限を満たすかを確かめてから、構成（プロンプトを短くする、ほかの候補）を選び直す。

    - A: 読み込みの割合を上げても、プロンプトの長さで決まる単価の切り替えは変わらない
    - B: thinking は出力として課金される。入力に足すのは数え方の誤り
    - C: fast mode は Haiku の対象外。この構成で割増が付いた原因ではない

    根拠: [モデルの階層の選択](../notes/02-models-prompting-context/model-tier-selection.md)、[コンテキストの構成とトークンの経済性](../notes/02-models-prompting-context/context-token-economics.md)

**問4** 地域の病院グループが、患者からのメッセージへの返信の下書きを作るエージェントを入れた。エージェントは電子カルテを検索して下書きを作り、看護師が送る前に確認する。リリース前の評価は次のとおりで、すべて合格だった。リリースから2週間で、別の患者の氏名と検査値を含む下書きが3件見つかった（どれも看護師が送信前に気づいた）。評価に足すべきものとして最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

```text
評価セット v2: 外来の典型的な問い合わせ 500 件
- 回答の正確さ（参照回答との一致を LLM が判定）: 93%（しきい値 90%）
- p95 の応答時間: 6.1 秒（しきい値 10 秒）
- 1件あたりの費用: $0.04（しきい値 $0.06）
```

<div class="quiz" data-answer="D" data-domain="4" markdown>

- A. 評価セットを同じ分布のまま 2,000 件に増やし、正確さの信頼区間を狭くする
- B. 正確さのしきい値を 95% に上げ、参照回答との一致を判定役により厳しく採点させる
- C. 看護師の確認があるので評価は足さず、本番で見つかった件数を月次で上に報告する

??? success "答えと解説"
    **正解: D。** 失敗は安全（プライバシー）の軸で、評価にその軸が無かった。指標・しきい値に加え、失敗の型を含む事例を足して、リリース前に検出できるようにする。

    - A: 失敗の型が無い分布のまま件数を増やしても、その型は見つからない
    - B: 正確さの軸を締めても、安全の軸が無いままになる
    - C: 本番の件数の報告は、検出がリリース後になる。看護師の確認は残る網であって、評価の代わりではない

    根拠: [評価の抜けを見つける](../notes/04-evaluation-testing/evaluation-coverage-gaps.md)

**問5** 精密機械メーカーの基盤チームが、Claude Code の管理設定で次の権限ルールを配った。狙いは「本番のクラスターを変える操作は止め、状態の参照は確認なしで許す」ことだ。ところが開発者から、`kubectl get pods` まで止められると苦情が来た。最も適切な直し方はどれか。（1つ選べ）
{ .quiz-q }

```json
{
  "permissions": {
    "deny": ["Bash(kubectl *)"],
    "allow": ["Bash(kubectl get *)", "Bash(kubectl describe *)"]
  }
}
```

<div class="quiz" data-answer="A" data-domain="5" markdown>

- A. 広い deny をやめ、`kubectl apply` や `kubectl delete` など変更系の操作に絞った deny にする
- B. allow を deny より前の行に書き、参照のルールのほうが先に当たるようにする
- C. deny は残し、`kubectl get` に確認を出す ask ルールを足して、開発者が毎回承認する
- D. deny をやめ、システムプロンプトに「本番のクラスターを変える kubectl は使わない」と書く

</div>

??? success "答えと解説"
    **正解: A。** 権限ルールは deny → ask → allow の順に評価され、最初に当たったもので決まる。広い deny に狭い allow で例外は作れないので、害が起きる操作（変更系）に絞って deny を置く。

    - B: 評価の順はファイルの書き順ではなく deny → ask → allow で決まる。参照もやはり deny に当たる
    - C: ask は deny の後に評価されるので、deny に当たる限り止まったまま。承認の手間も増える
    - D: プロンプトの指示は強制にならない。害の手前で、モデルの外の仕組みで止める
    - 残るリスク: 引数のパターンは言い換えで外れうる。PreToolUse フックで検証を重ねても文字列の検査なので万全ではなく、実行環境の層（サンドボックス、資格情報を外で注入する仕組み）で届く範囲を狭める制御も重ねる

    根拠: [ガードレールの置き場所](../notes/05-governance-safety/guardrail-placement.md)

**問6** 物流のアサギ運輸が、荷主ごとの月次の配送分析を数時間かけて作る非同期のエージェントを作る。社内には、エージェントのループやセッションの状態、サンドボックスを運用できる人がいないため、それらは任せたい。会社は AWS を主に使っており、調達の担当は「Amazon Bedrock なら請求をまとめられる」と言う。法務は、データの所在や保持に特別な制約は無いと確認済みだ。最も適切な構成はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="A" data-domain="1" markdown>

- A. Claude API の上で Claude Managed Agents を使い、ループ・状態・サンドボックスを任せる
- B. Amazon Bedrock を選び、その上で Claude Managed Agents を動かして運用を任せる
- C. Amazon Bedrock を選び、Agent SDK を自社のコンテナで動かして状態を自社で保存する
- D. Amazon Bedrock を選び、Messages API のループを自社で書いてセッションを保存する

</div>

??? success "答えと解説"
    **正解: A。** 効いている制約は「ループと状態を自社で運用できない」こと。所在の制約は無いので、ホスト型の実行環境（Managed Agents）が使えるデプロイ先を選ぶ。Managed Agents は Bedrock では使えない。

    - B: Bedrock では Managed Agents が使えない
    - C: 状態とサンドボックスを自社で運用することになり、外せない制約に反する
    - D: ループもセッションも自社で持つ構成で、運用の負担が最も大きい
    - 残るもの: Managed Agents はベータで、状態をサーバー側に持つので ZDR と HIPAA の対象外。将来その要件が出たら見直す

    根拠: [デプロイ先と実行環境の選択](../notes/01-solution-design/deployment-surface-runtime.md)

    - C: 回答は規程 7.1 に支えられている。ハルシネーションへの対策で、この失敗には効かない
    - D: 取り決めは規程の文書に無いので、検索を深くしても取れない
