## 問1〜15

**問1** 物流のアサギ運輸で、配送伝票の不備を分類する仕組みのモデル構成を見直している。要件は「社内の評価セット 1,200 件で正答率 95% 以上」「p95 3 秒以内」「月額 $2,500 以内」。今期の経営が掲げた価値の柱は「ソリューションのコスト」で、要件を満たしたまま月額を下げることを求めている。評価の結果は次のとおり。最も適切な構成はどれか。（1つ選べ）
{ .quiz-q }

| 構成 | 正答率 | p95 | 月額の見込み |
|---|---|---|---|
| Opus 5.5 / `medium`（現行） | 98.1% | 2.6 秒 | $2,400 |
| Sonnet 5.5 / `medium` | 97.4% | 1.9 秒 | $1,300 |
| Sonnet 5.5 / `low` | 95.6% | 1.4 秒 | $900 |
| Haiku 5.5 / `medium` | 93.8% | 0.8 秒 | $150 |

<div class="quiz" data-answer="C" data-domain="1" markdown>

- A. 正答率が最も高い Opus 5.5 / `medium` を続け、予算の残りで正答率をさらに上げる
- B. 最も速く安い Haiku 5.5 / `medium` に替え、足りない正答率は後からプロンプトで補う
- C. 要件をすべて満たす中で最も安い Sonnet 5.5 / `low` に替える
- D. 正答率と速さの釣り合いが良い Sonnet 5.5 / `medium` に替える

</div>

??? success "答えと解説"
    **正解: C。** まず上限（正答率・p95・月額）を破る案を外し、残りを問われた柱で比べる。柱が「ソリューションのコスト」なので、要件を満たす中で最も安い案が勝つ。

    - A: 要件の上で品質を伸ばしても、問われた柱（コスト）は伸びない。現行のままでは月額も下がらない
    - B: 正答率 93.8% は要件を割る。評価で確かめていない「後から補う」は、上限で外す段を飛ばしている
    - D: 要件は満たすが、同じ要件を満たすより安い案（$900）がある。釣り合いは問われた柱ではない

    根拠: [価値にもとづく設計の判断](../notes/01-solution-design/value-based-decisions.md)

**問2** 社内の開発基盤チームが、Claude Code のサブエージェント `build-runner` を配っている。役割はビルドとテストの実行で、`Bash` が要る。誤ってファイルを消す事故を防ぐため、frontmatter に `disallowedTools` の1行を足したところ、`build-runner` がビルドのコマンドをまったく実行できなくなった。「Bash は残し、`rm` だけを止める」という目的に合う直し方として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

```yaml
---
name: build-runner
description: ビルドとテストを実行し、失敗の要約を返す
tools: Read, Grep, Glob, Bash
disallowedTools: Bash(rm *)
---
```

<div class="quiz" data-answer="A" data-domain="3" markdown>

- A. frontmatter の `disallowedTools` を外し、settings の `permissions.deny` に `Bash(rm *)` を書く
- B. `disallowedTools` を `Bash(rm -rf *)` に狭め、ほかの形の `rm` は通すことにする
- C. `tools` から `Bash` を外し、ビルドの実行は親のエージェントに頼むようにする
- D. `disallowedTools` を外し、サブエージェントの本文に「rm は使わないこと」と書く

</div>

??? success "答えと解説"
    **正解: A。** サブエージェントの frontmatter の `disallowedTools` に `Bash(rm *)` と書くと、Bash ツールごと外れる。Bash を残して特定のコマンドだけ止めるなら、settings の `permissions.deny` に書く。

    - B: パターンを狭めても、frontmatter に書く限り Bash ツールごと外れる症状は変わらない
    - C: 役割に要る Bash を失い、ビルドとテストを任せるという分担そのものが崩れる
    - D: 本文の指示は強制にならない。見えているツールは誤った判断で呼ばれうる

    根拠: [最小権限のツール構成](../notes/03-integration/least-privilege-tools.md)

**問3** 医療機器メーカーのサポート窓口で、問い合わせを「不具合の報告（当局への報告の要否の確認が要る）」「使い方」「注文」など8つに振り分ける。1日 30万件、p95 1.2 秒以内、評価セットでの正答率 96% 以上、月額 $3,000 以内が要件だ。評価の結果は次のとおり。最も適切な構成はどれか。（1つ選べ）
{ .quiz-q }

| 構成 | 正答率 | p95 | 月額 |
|---|---|---|---|
| Haiku 5.5 / `low` | 94.2% | 0.6 秒 | $600 |
| Haiku 5.5 / `high` | 96.5% | 1.1 秒 | $1,100 |
| Sonnet 5.5 / `medium` | 97.8% | 1.6 秒 | $5,800 |
| Opus 5.5 / `low` | 98.0% | 2.3 秒 | $9,500 |

<div class="quiz" data-answer="D" data-domain="2" markdown>

- A. 正答率が最も高い Opus 5.5 / `low` にし、遅延はストリーミングで見かけを縮める
- B. Sonnet 5.5 / `medium` にし、予算を超える分は増額を申請して認めてもらう
- C. 最も安い Haiku 5.5 / `low` にし、足りない正答率は few-shot の例を足して埋める
- D. 品質・遅延・月額の3つを同時に満たすのは Haiku 5.5 / `high` だけなので、これを採る

</div>

??? success "答えと解説"
    **正解: D。** すべての制約を同時に満たす中で最も安い構成を、自分の評価セットで選ぶ。3つを満たすのは Haiku 5.5 / `high` だけ。同じモデルの effort を上げて品質の下限に届かせている。

    - A: p95 も月額も上限を破る。ストリーミングは見かけの話で、制約に示された p95 は変わらない
    - B: p95 1.6 秒と月額の両方で上限を破る。上限を超える案は価値が高くても外す
    - C: 正答率が下限を割る。例を足した構成は評価していないので、選ぶ根拠が無い

    根拠: [モデルの階層の選択](../notes/02-models-prompting-context/model-tier-selection.md)

**問4** 地域の病院グループが、患者からのメッセージへの返信の下書きを作るエージェントを入れた。エージェントは電子カルテを検索して下書きを作り、看護師が送る前に確認する。リリース前の評価は次のとおりで、すべて合格だった。リリースから2週間で、別の患者の氏名と検査値を含む下書きが3件見つかった（どれも看護師が送信前に気づいた）。評価に足すべきものとして最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

```text
評価セット v2: 外来の典型的な問い合わせ 500 件
- 回答の正確さ（参照回答との一致を LLM が判定）: 93%（しきい値 90%）
- p95 の応答時間: 6.1 秒（しきい値 10 秒）
- 1件あたりの費用: $0.04（しきい値 $0.06）
```

<div class="quiz" data-answer="B" data-domain="4" markdown>

- A. 正確さのしきい値を 95% に上げ、参照回答との一致をもっと厳しく判定させる
- B. 対象外の患者の個人情報を含む下書きの割合を指標にし、しきい値と、同姓の患者がいる事例などを足す
- C. 看護師の確認があるので評価は足さず、本番で見つかった件数を月次で報告する
- D. 評価セットを同じ分布のまま 2,000 件に増やし、正確さの信頼区間を狭める

</div>

??? success "答えと解説"
    **正解: B。** 失敗は安全（プライバシー）の軸で、評価にその軸が無かった。指標・しきい値に加え、失敗の型を含む事例を足して、リリース前に検出できるようにする。

    - A: 正確さの軸を締めても、安全の軸が無いままになる
    - C: 本番の件数の報告は、検出がリリース後になる。看護師の確認は残る網であって、評価の代わりではない
    - D: 失敗の型が無い分布のまま件数を増やしても、その型は見つからない

    根拠: [評価の抜けを見つける](../notes/04-evaluation-testing/evaluation-coverage-gaps.md)

**問5** 精密機械メーカーの基盤チームが、Claude Code の管理設定で次の権限ルールを配った。狙いは「本番のクラスターを変える操作は止め、状態の参照は確認なしで許す」ことだ。ところが開発者から、`kubectl get pods` まで止められると苦情が来た。最も適切な直し方はどれか。（1つ選べ）
{ .quiz-q }

```json
{
  "permissions": {
    "deny": ["Bash(kubectl *)"],
    "allow": ["Bash(kubectl get *)", "Bash(kubectl describe *)"]
  }
}
```

<div class="quiz" data-answer="B" data-domain="5" markdown>

- A. allow を deny より前の行に書き、参照のルールのほうが先に当たるようにする
- B. 広い deny をやめ、`kubectl apply` や `kubectl delete` など変更系の操作に絞った deny にする
- C. deny は残し、`kubectl get` に確認を出す ask ルールを足して、開発者が毎回承認する
- D. deny をやめ、システムプロンプトに「本番のクラスターを変える kubectl は使わない」と書く

</div>

??? success "答えと解説"
    **正解: B。** 権限ルールは deny → ask → allow の順に評価され、最初に当たったもので決まる。広い deny に狭い allow で例外は作れないので、害が起きる操作（変更系）に絞って deny を置く。

    - A: 評価の順はファイルの書き順ではなく deny → ask → allow で決まる。参照もやはり deny に当たる
    - C: ask は deny の後に評価されるので、deny に当たる限り止まったまま。承認の手間も増える
    - D: プロンプトの指示は強制にならない。害の手前で、モデルの外の仕組みで止める
    - 残るリスク: 引数のパターンは言い換えで外れうる。PreToolUse フックで検証を重ねても文字列の検査なので万全ではなく、実行環境の層（サンドボックス、資格情報を外で注入する仕組み）で届く範囲を狭める制御も重ねる

    根拠: [ガードレールの置き場所](../notes/05-governance-safety/guardrail-placement.md)

**問10** 重機メーカーのカナメ重工が、Claude Managed Agents で設計図面の質問に答えるエージェントを動かしている。構成は次のとおり。来月から外部の協力会社の技術者も使い始めるが、協力会社は契約した部品の図面しか見てはならない。また品質監査で「ある日の回答が、どのエージェントの定義と環境の設定で作られたか」を示すよう求められた。この2つの条件に備えて行うべき変更はどれか。（2つ選べ）
