## 問1〜15

**問1** 食品卸のアオバ商事で、経理の担当がファイルを渡さずに「先月公表された、経費精算に関わる税制の改正点を一覧にして」と頼んだ。返ってきた一覧には、施行日と条文の番号が断定的に書かれている。この一覧の扱いとして最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="C" data-domain="2" markdown>

- A. 条文の番号まで具体的なので、確かめた上で書かれた内容とみなして使う
- B. research を有効にして同じ一覧を作り直させ、新しい一覧をそのまま使う
- C. 最近の改正は学習データに無いことがあるので、施行日や条文を公式の資料で確かめる
- D. 施行日だけを公式の資料で確かめ、条文の番号は細部なので確かめずに載せる

</div>

??? success "答えと解説"
    **正解: C。** 最近の出来事は学習データに無いことがあり、資料を渡さずに求めた具体値は根拠の無いまま断定で書かれやすい。具体値ごとに公式の資料で確かめる。

    - A: 言い切りが強く詳しい箇所ほど信用するのは、ハルシネーションを見落とす典型
    - B: research の出力も、引用元を開いて確かめるまでは使えない。作り直しは確認の代わりにならない
    - D: 条文の番号も根拠の無い具体値になりうる。具体値ごとに「どこに書いてあるか」を確かめる

    根拠: [ハルシネーションの見つけ方](../notes/02-output-evaluation/hallucination-patterns.md)

**問2** 工具メーカーのカガミ工業で、営業の担当が依頼の冒頭に「あなたは一流の営業コンサルタントです」と書き、商談の後のフォローメールを頼んだ。返ってきたメールは整っているが、どの相手にも送れる内容で、この商談の経緯が反映されていない。最も適切な直し方はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="A" data-domain="1" markdown>

- A. 役割の一文は残してよいが、商談の経緯、相手の立場、メールで決めてほしいことを書き足す
- B. 役割を「世界一の営業コンサルタント」に強め、経験年数などの設定も細かく足す
- C. 「もっと相手に寄り添った内容に」とだけ返し、同じ会話で書き直させる
- D. フォローメールの一般的な書き方の原則を、依頼の冒頭に長く説明しておく

</div>

??? success "答えと解説"
    **正解: A。** 一般論が返るのは、Claude が既定では知らない文脈（この商談の経緯、読み手、目的）が欠けているから。役割だけでは足りず、文脈を渡す。

    - B: 役割を作り込んでも、Claude が知らない商談の事実は埋まらない
    - C: 「もっと〜」とだけ返しても、足りない文脈は埋まらない
    - D: 一般的な書き方は Claude が既に知っている。書き足すべきは Claude が知り得ない事実

    根拠: [プロンプトの組み立て](../notes/01-task-definition-prompting/prompt-construction.md)

**問3** 家具販売のモクレン家具で、経理部が経費精算の流れを見直している。ステップは ①領収書の内容の一覧化 ②社内規程に照らした「要確認」の候補出し ③精算の承認と振込の確定 ④規程違反が疑われる社員への聞き取り の4つだ。振り分けとして最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="D" data-domain="4" markdown>

- A. 4つとも AI が実行し、月末に経理課長がまとめて結果に目を通す
- B. ①②は人が持ち、③④を AI が実行して、時間のかかる処理を速める
- C. 規程の判断が絡む業務なので、経費精算では業務ごと AI を使わない
- D. ①は AI が実行、②は AI の候補を人がレビュー、③④は人が持つ

</div>

??? success "答えと解説"
    **正解: D。** 取り消せて影響の小さい一覧化は AI に任せ、判断に影響する候補出しは人がレビューし、責任や共感が要る承認・聞き取りは人が持つ。ステップごとに振り分ける。

    - A: 承認や聞き取りまで AI に通す任せすぎ。月末にまとめて見るのは実質的なレビューにならない
    - B: 振り分けが逆。責任と共感が要るステップを AI に渡している
    - C: 業務を丸ごと任せる・任せないで決めると、任せられるステップまで捨てる

    根拠: [任せる・人が持つ・人がレビューするの振り分け](../notes/04-workflow-design/delegation-workflow-redesign.md)

**問4** 資格講座を運営するミライ学院の教務担当が、修了試験の記述式の答案を Claude に読ませ、受講者ごとの合否の判定案と理由を書かせる案を出した。判定は受講者の修了資格を左右する。この案の分類として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="B" data-domain="6" markdown>

- A. 適切。採点の基準が決まっているので、通常の見直しで足りる
- B. 安全策つきで適切。講師が判定を確かめて変えられるようにし、受講者に AI の関与を伝える
- C. 不適切。教育の判定は Usage Policy の禁止事項なので、Claude を使わない
- D. 適切。最後に事務局が一覧に目を通すので、受講者への開示は要らない

</div>

??? success "答えと解説"
    **正解: B。** 教育・資格の判定は、特定の個人を判断する高リスクの用途。資格のある人の実質的な確認と本人への開示を付ければ、安全策つきで適切になる。

    - A: 個人への重い判断なので、内部の下書きと同じ通常の見直しでは足りない
    - C: 教育の判定は禁止事項ではなく高リスクの用途。安全策で使える案まで捨てている
    - D: 一覧に目を通すだけでは、判定を評価して変えられる確認にならず、開示も欠ける

    根拠: [ユースケースの適切さの分類](../notes/06-responsible-use/use-case-appropriateness.md)

{ .quiz-q }

<div class="quiz" data-answer="A" data-domain="3" markdown>

**問6** 精密部品のサクラ電子で、経理部は「月次決算」の Project を使っている。Project instructions に決算資料を作る長い手順を書き込んだところ、同じ Project で勘定科目のちょっとした質問をしても、手順に沿った長い回答が返るようになった。最も適切な直し方はどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="D" data-domain="5" markdown>

- A. instructions の手順の前に「関係のない質問のときは手順を無視する」と書き足す
- B. 手順を Project の説明欄（description）に移し、instructions を短くする
- C. 手順の全文を knowledge のファイルにして、すべてのチャットで参照させる

    - B: Project の説明欄は Claude からは見えないので、手順そのものが効かなくなる
    - C: knowledge も Project の全チャットで使われるので、問題の構造は変わらない

**問11** 製菓メーカーのシラユキ製菓で、経理の担当が取引先との契約書（アップロード済み）から、支払条件の一覧を作って社内に回したい。契約書に無い条件が一覧に混じるのを防ぎたい。依頼と点検のやり方として適切なものはどれか。（2つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="A,D" data-domain="2" markdown>

- A. 一覧の各項目に契約書の該当箇所の原文を引用させ、引用の無い項目は外させる
- B. できた一覧について「契約書と食い違いはあるか」と聞き、無いと言われれば回す
- C. 「絶対に間違えないで」と依頼に書き、強く念押しした上で一覧を作らせる
- D. 契約書に書かれていない条件は「記載なし」と答えてよいと、依頼の段階で伝える
- E. 契約書のうち支払条件に関係しそうな部分を Claude に要約させ、その要約から一覧を作らせる

</div>

??? success "答えと解説"
    **正解: A と D。** 主張ごとに資料の引用を付けさせて引用の無いものを外す（引用の点検）と、分からないと言ってよいと先に許す（依頼の段階の予防）が、資料に無い主張を減らす。

    - B: 書き終えたあとで Claude に聞くのは、独立した確認にならない
    - C: 強い念押しは、根拠の無い補完を防ぐ仕組みにならない
    - E: 要約を挟むと原文との対応が切れ、要約で落ちた条件や混じった補完を見分けられない。関係する箇所は原文のまま抜き出させる

    根拠: [使う前の検証](../notes/02-output-evaluation/verification-techniques.md)

**問12** 文具卸のコマチ商会で、経理の担当がコード実行で取引データ（CSV）を部署別に集計した。ところが部署別の合計が、会計システムの月次の合計とわずかに合わない。次の一手として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="C" data-domain="3" markdown>

- A. コードで計算した結果なので、会計システムの側の誤りとみなして報告する

- B. Claude に補償の案を3つ出させ、いちばん費用の少ない案を顧客に示す
- C. 謝罪のメールは Claude の文面を使い、誤字だけを確かめてから送る
- D. 謝罪は誤ると取り消せないので、この件では準備も含めて Claude を一切使わない

</div>

??? success "答えと解説"
    **正解: A。** 共感と責任が要る対応は人が持ち、AI は準備の資料づくりに使う。

    - B: 案を出させるのはよいが、どれを示すかを費用だけで機械的に決め、顧客との関係と責任を踏まえた人の判断を外している
    - C: 誤字だけの確認は形だけのレビューで、共感が要る文面を実質的に AI の出力のまま送っている
    - D: 準備のように任せられる部分まで捨てている

    根拠: [任せる・人が持つ・人がレビューするの振り分け](../notes/04-workflow-design/delegation-workflow-redesign.md)

- C. 推敲のチャットでは、使わない connector を「+」メニューから切る

- C. 新しいチャットで、交渉方針を最初から決め直してから提案書に進む

**問60** 介護用品のサツキ商事で、営業の担当が、毎週の営業日報を「要点をまとめて」と Claude に頼んでいる。課長が知りたいのは顧客の反応と次の打ち手だが、要約は毎回、訪問件数や受注額などの数字に偏る。原因と直し方として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }

<div class="quiz" data-answer="A" data-domain="1" markdown>

- A. あいまいな指示。「要点」を「顧客の反応と次の打ち手」と具体的に書き直す
- B. 制約の欠如。要約の長さを5行以内に決め、短くまとめさせる
- C. 種類に合わない戦略。research に切り替えて要約させ直す

    - B: 長さを決めても、何を要点とするかは決まらず、数字に偏ったまま短くなる
    - C: 要約に外の情報は要らず、戦略を替える場面ではない
    - D: 原因を当てる前に、モデルの力不足と決めている
