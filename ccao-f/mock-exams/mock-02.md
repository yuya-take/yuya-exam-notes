# 模擬試験 第2回

> 本番の採点される60問だけを作った。本番は70問（採点60＋採点外10）・120分なので、時間は本番のペースに合わせて 103分（120×60/70）にした。本番と同じく、1問ごとに独立した場面のシナリオ型で、ドメインは混ぜて並べている。第1回より、2つの観点を組み合わせて判断する問題と、複数の層の原因を切り分ける問題を多めにした。問題はすべて公式ドキュメントとこのリポジトリのノートから作った練習用で、本番の問題ではない。

## 問1〜15


**問1** 産業機器メーカーのトキワ機工で、法務の補助をする担当が、営業部向けに「売買契約書を締結前に確かめるためのチェックリストを作って」と頼んだ。どの会社にも当てはまる一般的な項目しか出なかったので、依頼の冒頭に「経験20年の企業法務の弁護士として」と足したが、出力はほとんど変わらない。次の一手として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }


<div class="quiz" data-answer="C" data-domain="1" markdown>

- A. 役割の文をさらに作り込み、専門分野や得意な契約の種類まで書き足す
- B. 「もっと具体的に、実務で使えるように」と書き足して頼み直す
- C. 自社が売り手であること、営業が締結前に使うこと、認めない条項と理由を書く
- D. 上位のモデルと高い effort に切り替えて、同じ依頼を送り直す

</div>


??? success "答えと解説"
    **正解: C。** 一般論しか返らない原因は、Claude が既定では知らない文脈（自社の立場、使い道、社内の事情）の欠落。役割を足しただけでは埋まらない。

    - A: 役割を細かく作り込んでも、自社の立場や読み手は伝わらない
    - B: 何が足りないかを伝えておらず、欠けた文脈は埋まらない
    - D: 上位の設定は、プロンプトの抜けを補わない

    根拠: [プロンプトの組み立て](../notes/01-task-definition-prompting/prompt-construction.md)

**問2** 経営コンサルティング会社のコンサルタントが、顧客の物流部門向けの中間報告書の下書きを Claude に作らせた。依頼では「顧客の部長向け、です・ます調、結論から」と指定した。下書きは論点も構成も合っているが、語調が社内メモのようにくだけている。また「来期から倉庫を1か所に統合すべき」とあるが、統合の可否は顧客の労使協議の状況しだいで、その情報は Claude に渡していない。最も適切な対応はどれか。（1つ選べ）
{ .quiz-q }


<div class="quiz" data-answer="A" data-domain="2" markdown>

- A. 語調は要件との差を示して直させ、統合の提言はコンサルタントが確かめて書き換える
- B. 語調も提言も含め、要件を全部書き直した依頼で、一から作り直させる
- C. 「顧客の事情を踏まえて正確に」と書き足し、提言の箇所も Claude に直させる
- D. 論点と構成は合っているので、語調だけを自分で直してそのまま提出する

</div>


??? success "答えと解説"
    **正解: A。** 語調のずれは指示で伝えられる差（修正が必要）。労使協議の状況は Claude の手元に無い情報なので、提言の箇所は人の手で直す。

    - B: 合っている論点と構成まで捨てる。作り直しても、手元に無い情報は埋まらない
    - C: Claude が持たない情報は、何度頼んでも埋まらない。もっともらしく作られるおそれもある
    - D: 根拠の無い提言が、顧客に出す報告書に残る

    根拠: [出力の評価と目的への適合](../notes/02-output-evaluation/fitness-for-purpose.md)

**問3** 独立系のコンサルタントが、次の3つの作業に Claude を使う。①今日だけ送る、打ち合わせのお礼メールの推敲 ②顧客Aの3か月の業務改善案件（契約書、現状調査の資料、用語集を何度も参照する） ③どの顧客でも同じ構成で作る週次の進捗報告。機能の組み合わせとして最も適切なものはどれか。（1つ選べ）
{ .quiz-q }


<div class="quiz" data-answer="D" data-domain="3" markdown>

- A. ①〜③をすべて1つの Project にまとめ、instructions に3つの作業の手順を書く
- B. ①は Project を作って記録を残し、②は memory に任せ、③は依頼のたびに構成を書く
- C. ①はふつうの chat、②は資料を Skill に入れ、③は顧客ごとの instructions に書き写す
- D. ①はふつうの chat、②は顧客Aの Project の knowledge に資料を置き、③は Skill にする

</div>


??? success "答えと解説"
    **正解: D。** chat に足りないものだけを機能で足す。一回きりの推敲は chat、案件の資料は Project の knowledge、どの案件でも同じ手順は Skill。

    - A: 無関係な仕事を1つの Project に混ぜ、一回きりの作業にまで機能を重ねている
    - B: 一回きりの相談に Project は要らない。決まった資料を memory に任せるのは向かない
    - C: 案件の資料は Project に置く。どの案件でも同じ書式を instructions に書き写すのはひっかけ

    根拠: [タスクに合う機能の組み合わせ](../notes/03-capability-model-context/capability-selection.md)

**問4** SaaS 企業のカスタマーサクセス担当が、Claude に「解約を減らす施策を考えて」とだけ頼んだ。返ってきたのは、どの業界にも当てはまる一般論だった。担当はその中の「利用率の低い顧客に毎月電話でフォローする」を、自社の体制で回せるかを確かめないまま、上司への提案資料に入れた。上司は担当が Claude を使うことを承知しており、担当も顧客データを Claude に渡していないことは分かっていた。上司からは、担当者1人あたりの顧客数では回せないと指摘された。4D のうち、この場面で欠けていたものはどれか。（2つ選べ）
{ .quiz-q }


<div class="quiz" data-answer="B,E" data-domain="4" markdown>

- A. Delegation。施策の案出しを Claude に任せたこと自体が誤りだった
- B. Description。自社の顧客層や体制など、役に立つ出力に要る文脈を伝えていない
- C. Transparency Diligence。AI を使ったことを上司に伝えていない
- D. Platform Awareness。Claude が自社の顧客データを読めると思い込んでいた
- E. Deployment Diligence。自社で回せるかを確かめないまま、出力を提案に使った

</div>


??? success "答えと解説"
    **正解: B、E。** 一般論が返ったのは文脈を伝えていない Description の欠け。確かめずに出力を使ったのは Diligence（Deployment）の欠け。

    - A: 案出しは AI に任せやすい作業で、任せたこと自体は誤りではない
    - C: 上司は Claude を使うことを承知している
    - D: 顧客データを渡していないことは、本人も分かっていた

    根拠: [AI Fluency の4D](../notes/04-workflow-design/ai-fluency-4d.md)

**問5** IT コンサルタントが、顧客Cの案件の Project を使っている。月次報告の作り方（集計の順序、見出し、表の形式）を3ページ分 Project instructions に書き込んだところ、同じ Project で「この用語の意味は？」のような短い質問をしても、月次報告の形式で答えが返るようになった。最も適切な直し方はどれか。（1つ選べ）
{ .quiz-q }


<div class="quiz" data-answer="B" data-domain="5" markdown>

- A. instructions の冒頭に「月次報告を頼まれたときだけ下の手順に従う」と足す
- B. 月次報告の手順を Skill に切り出し、instructions には役割・口調・制約を残す
- C. 月次報告の手順を knowledge のファイルに移し、instructions からは消す
- D. 短い質問は Project の外のチャットでするよう、チームの運用を変える

</div>


??? success "答えと解説"
    **正解: B。** Skill は関係する依頼のときだけ読み込まれるので、繰り返す手順を切り出すと、ほかのチャットの邪魔をしない。

    - A: 長い手順が、その Project の全チャットで読み込まれる状態は変わらない
    - C: knowledge も全チャットで背景として使われる。手順の置き場所は Skill が合う
    - D: 設定の問題を運用でよけているだけで、短い質問で Project の文脈を使えなくなる

    根拠: [Project の設定と、instructions・knowledge・Skill の使い分け](../notes/05-configuration-knowledge/project-configuration.md)、[Skills の仕組みと使いどころ](../notes/05-configuration-knowledge/skills.md)

**問6** 通販会社の商品企画チームが、Claude を使う3つの案を分類している。①社内の商品アンケートの自由記述を要約し、改善点を整理する ②購入履歴から顧客ごとに後払いの可否の推奨を作り、本人への通知に使う ③自社の新商品について、一般の購入者を装った好意的な口コミ文を作って投稿する。分類として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }


<div class="quiz" data-answer="A" data-domain="6" markdown>

- A. ①適切 ②安全策つきで適切（資格のある人の確認と本人への開示） ③不適切
- B. ①安全策つきで適切 ②不適切 ③安全策つきで適切（投稿の前に人が確認）
- C. ①適切 ②適切（通常の見直し） ③安全策つきで適切（AI で作ったと明記）
- D. ①安全策つきで適切 ②安全策つきで適切 ③安全策つきで適切（件数を絞る）

</div>


??? success "答えと解説"
    **正解: A。** 社内の要約は適切。個人の信用に関わる判断は高リスクの用途で、人の確認と開示をつけて初めて適切。購入者を装った口コミは禁止事項（偽装した活動）で、安全策を足しても使えない。

    - B: ②は要件を満たせば使える高リスクの用途。③の禁止事項は、人が確認しても使えない
    - C: ②は個人への判断なので、通常の見直しでは足りない。③は禁止事項
    - D: ①に重い手続きを課している。③の禁止事項は、件数を絞っても使えない

    根拠: [ユースケースの適切さの分類](../notes/06-responsible-use/use-case-appropriateness.md)、[Anthropic Usage Policy の要点](../notes/06-responsible-use/usage-policy.md)

**問7** 家電メーカーの商品企画担当が、web 検索を使わない chat で「競合のミドリ電機が先月発表した新型の空気清浄機の仕様と価格を教えて」と頼んだ。Claude は型番・価格・適用床面積を言い切って答えた。この答えについての見方として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }


<div class="quiz" data-answer="C" data-domain="2" markdown>

- A. 型番まで具体的に書かれているので、公式の発表にもとづく情報とみなしてよい
- B. 価格は変わりやすいので疑い、型番と仕様はそのまま企画書に使ってよい
- C. 先月の発表は学習データに無いことがあり、言い切った具体値ほど根拠を疑って確かめる
- D. 別のチャットでも同じ質問をし、答えが一致した値だけを使えば確かめたことになる

</div>


??? success "答えと解説"
    **正解: C。** 最近の出来事は学習データに無いことがあり、資料無しで求めた具体値は根拠の無いまま書かれやすい。

    - A: 詳しく言い切った箇所ほど信用するのはひっかけ。根拠を指せるかで見る
    - B: 型番や仕様も、根拠の無い具体値として作られうる
    - D: 毎回同じ答えだから正しい、とは言えない。公式の発表と照らす

    根拠: [ハルシネーションの見つけ方](../notes/02-output-evaluation/hallucination-patterns.md)

**問8** 化粧品会社の広報担当が、SNS の告知文を作らせている。依頼文の中に、過去の告知文を3件、指示と同じ段落に続けて貼った。すると出力に、例の1件にあった旧商品の名前と発売日が入ってしまう。また、3件とも冒頭が「＼新登場／」だったため、出力もすべてその書き出しになる。最も適切な直し方はどれか。（1つ選べ）
{ .quiz-q }


<div class="quiz" data-answer="D" data-domain="1" markdown>

- A. 「例の中身は使わない」「書き出しをまねない」と、依頼の最後に書き足す
- B. 例を1件に減らし、旧商品の名前と日付だけを伏せ字にして渡す
- C. 例をすべて外し、「親しみやすく、短く、印象的に」と書きぶりを言葉で伝える
- D. 例をタグや見出しで指示と分けて形式の見本と書き、書き出しの違う例にする

</div>


??? success "答えと解説"
    **正解: D。** 例と指示を区切れば、例の中身が今回の依頼の材料に読まれにくくなる。例どうしに違いを持たせれば、書き出しの癖が写りにくい。

    - A: 例は見せたまま残る。「まねないで」と書いても癖は写る
    - B: 例が1件だと、その長さや書き出しがかえって写りやすい
    - C: 形容詞では受け取り方に幅があり、形式がそろわない

    根拠: [例・資料・構造で狙いを伝える](../notes/01-task-definition-prompting/examples-and-structure.md)

**問9** コンサルタントが、顧客企業の売掛金の督促の流れを見直している。ステップは「未入金の取引先の一覧づくり」「督促メールの文面の作成と送信」「長く未入金の取引先との取引を止めるかの判断」の3つだ。振り分けとして最も適切なものはどれか。（1つ選べ）
{ .quiz-q }


<div class="quiz" data-answer="B" data-domain="4" markdown>

- A. 3つとも Claude が実行し、担当者は月末に結果の一覧と送信の記録だけを見る
- B. 一覧は Claude が作り、督促メールは Claude の下書きを人が確認して送り、取引停止は人が決める
- C. 一覧と取引停止の判断は Claude に任せ、督促文は関係を考えて人が一から書く
- D. 督促は取引先との関係に響くので、3つとも人が行い、Claude はどこにも使わない

</div>


??? success "答えと解説"
    **正解: B。** ステップごとに、取り消せるか・影響・人の判断の要否・責任で振り分ける。社外に出る督促文は人のレビュー、取り消しにくい取引停止は人が持つ。

    - A: 社外に出る督促文と、取り消しにくい取引停止の判断まで任せすぎている
    - C: 取引停止は人の判断と責任が要る。督促文の下書きは任せられる
    - D: 業務単位で決めていて、任せられるステップまで捨てている

    根拠: [任せる・人が持つ・人がレビューするの振り分け](../notes/04-workflow-design/delegation-workflow-redesign.md)

**問10** 食品メーカーの PM が、新商品の需要の見通しを Claude で多段に分析させている。過去3年の販売の集計（コード実行で計算済み）、販促の計画、競合の動きの資料を渡し、見る観点と手順も依頼に書いた。結果は役員会での生産量の判断に使う。既定の設定のままでは、季節の要因と販促の効果を分けずにまとめるなど、推論が浅い。最も適切な対応はどれか。（1つ選べ）
{ .quiz-q }


<div class="quiz" data-answer="A" data-domain="3" markdown>

- A. effort を上げるか上位のモデルに替え、同じ依頼でより深く考えさせる
- B. 資料がまだ足りないとみて、関係の薄い業界の資料まで足して渡し直す
- C. 使用量を節約するため、軽いモデルに下げて何度か出し直して比べる
- D. 設定は既定のまま、「もっと深く考えて」と書き足して出し直す

</div>


??? success "答えと解説"
    **正解: A。** 文脈と資料がそろっていて、複雑で誤りの影響が大きい分析なのに推論が浅いなら、上位のモデルや高い effort を選ぶ。

    - B: 文脈は足りている。関係の薄い資料を足すと、かえって答えに混ざる
    - C: 誤りの影響が大きい分析で、使用量を惜しんで軽い設定にするのはひっかけ
    - D: 設定を変えずに念を押すだけで、既定の考える量のまま

    根拠: [モデルの階層と effort レベルの選び方](../notes/03-capability-model-context/model-effort-selection.md)

**問11** 人材サービス会社で法務の補助をする担当が、営業部の依頼で、取引先から届いた業務委託契約書の修正案を Claude で作った。修正案は損害賠償の上限の条項を書き換えている。担当は、Claude が挙げた法令の条文を公式の法令データベースで開き、実在し内容も合うことを確かめた。取引先に送る前に、次にすべきことはどれか。（1つ選べ）
{ .quiz-q }


<div class="quiz" data-answer="C" data-domain="2" markdown>

- A. 条文を確かめたので、そのまま営業部に戻して取引先へ送ってもらう
- B. 別のチャットで Claude に修正案を見せ、問題が無いかを確かめさせる
- C. 社内の法務の責任者か弁護士のレビューに回し、承認を得てから送る
- D. 修正案に「AI が作成した案です」と書き添えて、取引先に判断を委ねる

</div>


??? success "答えと解説"
    **正解: C。** 契約の条項は社外に出て法的な影響があり、出典を開いても専門家でなければ読み違えうる。自分で正しさを判断できない専門の判断は、専門家や責任者のレビューに回す。

    - A: 条文が実在しても、条項の書き換えが妥当かという判断は残っている
    - B: Claude の中だけで完結する確認で、独立した確認にならない
    - D: AI の関与を書いても、中身の責任は出力を使って渡した側に残る

    根拠: [レビューの深さとエスカレーション](../notes/02-output-evaluation/review-depth-escalation.md)、[使う前の検証](../notes/02-output-evaluation/verification-techniques.md)

**問12** 賃貸住宅の管理会社で、業務分析担当が、入居審査の結果を申込者に伝える文書を Claude で下書きする案を検討している。否決のときは、その理由も書く。Usage Policy に沿った運用として最も適切なものはどれか。（1つ選べ）
{ .quiz-q }


<div class="quiz" data-answer="B" data-domain="6" markdown>

- A. 社内の審査の分析資料と同じ扱いにし、担当者がいつもどおり誤字を見直して送る
- B. 審査を評価できる担当者が中身を確かめて変えられるようにし、AI の使用を申込者に伝える
- C. 住宅の審査は Usage Policy の禁止事項に当たるので、文書の下書きにも使わない
- D. 承認の通知は Claude の文書をそのまま送り、否決の通知では AI の関与を伏せて送る
